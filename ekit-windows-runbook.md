# ekit on Windows: Runbook and Benchmark Guide

This guide covers running the Enterprise SDD Kit (`ekit`) on Windows when GitHub Spec Kit
(`specify`) and OpenCode already work on the machine. It also explains how to measure the
kit against plain Spec Kit.

> **Status:** MVP1 (ekit 0.1.5, kit 0.1.6) was verified on Linux against Spec Kit 1.2.7. It is written to be
> OS-agnostic, but this is its first Windows run, so treat the first project as the pilot.

---

## 1. Dependencies and assumptions

### Required on the machine

| Dependency | Version | Needed for | Check with |
|---|---|---|---|
| Windows | 10 / 11 | — | — |
| PowerShell | 7.x recommended (5.1 works) | running commands | `$PSVersionTable.PSVersion` |
| Git for Windows | 2.40+ | kit from git, ledger commit tracking, feature-branch detection | `git --version` |
| uv | 0.5+ | installing `ekit`; Python stacks | `uv --version` |
| Python | 3.11+ (uv can provide it) | running `ekit` and Spec Kit's Python scripts | `python --version` |
| Spec Kit CLI (`specify`) | 1.0+ (tested 1.2.7) | everything | `specify version` |
| OpenCode | current, with a model provider configured | running the slash commands | `opencode --version` |

### Required per stack

| Stack | Additional dependencies |
|---|---|
| `fastapi-jinja` | none beyond uv/Python (dependencies are added by the landing-zone step) |
| `fastapi-react` | Node.js 20 LTS+ and npm |
| `springboot-vanilla` | JDK 21 with `JAVA_HOME` set (the Maven wrapper is generated by the landing-zone step, so no global Maven is needed) |
| `springboot-react` | JDK 21 + `JAVA_HOME`, Node.js 20 LTS+ and npm |
| Any `@ui` (browser) scenario | Playwright browsers, installed by the landing-zone step |

### Assumptions the commands rely on

1. `ekit`, `specify`, `opencode`, `git` and `uv` are on `PATH` in the terminal you use.
   After installing ekit, run `uv tool update-shell` once and open a new terminal.
2. You run `ekit` commands from the project root, or any folder below it. ekit finds the
   project by looking upward for `.ekit\project.yaml`.
3. Feature work happens on the branch Spec Kit creates (`001-feature-name`). ekit uses that
   branch name to find the active feature. If you are not on the branch, add
   `--feature 001-feature-name`, or set the environment variable:
   `$env:SPECIFY_FEATURE = "001-feature-name"`.
4. One PRD per folder under `docs\requirements\<slug>\`. If there is more than one PRD, pass
   `--prd docs/requirements/<slug>` to `intake`, `ready` and `questions`.
5. Everything ekit creates gets committed, including `.ekit\` with `kit.lock.yaml`,
   `ledger\` and `policy.overrides.yaml`. The ledger is the evidence that tests failed
   (red) before the code made them pass (green).
6. Do not edit files in `.ekit\kit\` by hand. Change the kit at its source and run
   `ekit upgrade`. `ekit doctor` flags local edits.
7. Long paths (relevant for `node_modules`): run
   `git config --global core.longpaths true` once. If Windows still complains, enable
   *Win32 long paths* in Group Policy or the registry.
8. **Python environments are project-local (ENV-01).** Python stacks always use a `.venv`
   in the backend folder, created by uv from `uv.lock`, and pinned by `.python-version`.
   - You never activate it. `ekit run …` and the agents call `uv run --locked`, which uses
     `.venv\Scripts\python.exe` automatically.
   - Never `pip install` into the global Python.
   - After cloning a project, run `ekit run install` once.
   - If uv doesn't find the pinned Python on the machine, it downloads it.

   React uses a local `node_modules` (`npm ci`, `.nvmrc`). Spring Boot uses the Maven
   wrapper. `ekit gate baseline` and `ekit gate green` fail if an environment folder is
   committed, isn't in `.gitignore`, or doesn't match its pinned version.
9. Line endings don't matter. The kit hash ignores CRLF vs LF, so `core.autocrlf=true`
   is fine.
10. **Everyone runs the same ekit CLI version.** The rules are pinned in the repository, but the
    CLI that applies them is installed per machine. The project records the agreed CLI version in
    `.ekit\kit.lock.yaml`; install exactly that tag. See *What is pinned, and what is not* below.

### What is pinned, and what is not

| Part | Where it lives | Pinned by | Changes when |
|---|---|---|---|
| **Rules**: gate policy, NFR catalogue, stack profiles, templates, agent rules | `.ekit/kit/` in the repository (committed) | `.ekit/kit.lock.yaml`: source, resolved commit, sha256 | someone runs `ekit upgrade` and commits the result |
| **Check engine**: the `ekit` CLI that reads those rules and judges the files (`checks.py`, `gates.py`, step scan, fingerprints) | each machine's uv tool folder | `ekit.version` in `.ekit/kit.lock.yaml` (since ekit 0.1.4), plus the kit's allowed range `requires.ekit` (e.g. `>=0.1.5,<0.2`) | a developer reinstalls the CLI |

Both parts decide a gate result. Identical rules judged by two different CLI versions can disagree,
because check logic changes between releases (0.1.1 changed how tags are read, 0.1.2 added
`RED-STEPS-ASSERT` and `GREEN-TESTS-UNCHANGED`, 0.1.5 stopped counting skipped scenarios as red). So:

- **One CLI version per project.** `ekit init` and `ekit upgrade` record the running CLI version in the lock.
  Everyone, and CI, installs exactly that version.
- **Install by tag.** Tag the kit repository with the CLI version (e.g. `v0.1.5`; one tag then fixes both the CLI
  and the kit it ships) and install it with `uv tool install --force git+https://…/sdd-kit.git@v0.1.5`.
- **Mismatch is visible.** `ekit doctor` fails the row *ekit CLI matches the project pin*, `ekit status` prints a
  `!!` line, and every gate report (text, JSON and JUnit) carries a note naming both versions.
- **CI refuses to judge with the wrong CLI.** Set `EKIT_REQUIRE_PINNED_CLI=1` in the pipeline: a gate then exits 2
  before running any check if the installed CLI differs from the pin.
- **Moving the team to a new CLI is a reviewed change.** Install the new CLI, run `ekit upgrade` (re-vendors the
  kit and re-pins the CLI), commit `.ekit/`, and have everyone reinstall the same tag after the merge.
- **`bundled` couples the two.** With `--source bundled`, `ekit upgrade` vendors the kit shipped inside the CLI you
  are running, so whoever upgrades also chooses the kit version. Teams should prefer a git source pinned to a tag.
- **Evidence names its judge.** Every red and green ledger entry records `ekit_version` next to `kit_version`.

Check what you run before comparing gate results with anyone: `ekit --version`, then `ekit doctor`.

## 2. Where and how to launch

| What | Where | How |
|---|---|---|
| `ekit ...` commands | **Windows Terminal / PowerShell**, in the project root | normal CLI |
| `/speckit.*` slash commands | **inside OpenCode**, started from the project root | `cd C:\work\my-project` then `opencode` |
| Gates (`ekit gate ...`) | either place. OpenCode runs them itself as part of each slash command; you can also run them in PowerShell to check state | — |

Two windows side by side work well: OpenCode on the left, PowerShell on the right for
`ekit status` and `ekit gate ...`.

> Always launch OpenCode from the **project root**. It reads `AGENTS.md`,
> `.opencode\commands` and `.opencode\agents` from there. If you start it elsewhere, the
> slash commands and rules won't load.

## 3. Commands by frequency

### A. Once per machine

```powershell
# 1. Unzip the kit somewhere permanent
Expand-Archive "$HOME\Downloads\enterprise-sdd-kit.zip" -DestinationPath C:\tools

# 2. Install the ekit CLI and put uv tools on PATH
uv tool install C:\tools\enterprise-sdd-kit
uv tool update-shell        # then open a NEW terminal

# 3. Git settings (if not already set)
git config --global core.longpaths true

# 4. Verify
ekit --version
ekit stacks
ekit doctor                 # outside a project it checks tools only
```

Optional, to make your team's kit the default source for every `init`:

```powershell
[Environment]::SetEnvironmentVariable("EKIT_KIT_SOURCE", "git+https://git.example.com/eng/sdd-kit.git@v0.1.5", "User")
# use the same tag for the CLI itself:
uv tool install --force git+https://git.example.com/eng/sdd-kit.git@v0.1.5
```

### B. When the kit itself changes (new kit version)

```powershell
# Reinstall the CLI from the new tag (preferred) or the updated folder
uv tool install --force git+https://git.example.com/eng/sdd-kit.git@v0.1.5
# or: uv tool install --force C:\tools\enterprise-sdd-kit
ekit --version
```

Projects do **not** change automatically, and until they do, `ekit doctor` reports that your CLI no
longer matches their pin. Move a project deliberately, as one reviewed change:

```powershell
cd C:\work\loan-origination
ekit upgrade                      # re-vendors the kit and re-pins the CLI version in kit.lock.yaml
ekit doctor
git add .ekit; git commit -m "chore: ekit 0.1.5 / kit 0.1.6"
```

After the merge, everyone on the project (and the CI image) installs the same tag. Until then, keep
the previous CLI for projects that have not moved: `uv tool install --force git+…@v<previous>`.

### C. Once per project

**New project (greenfield):**

```powershell
cd C:\work
ekit init loan-origination --stack fastapi-react
#   asks for the kit source (bundled / local folder / git). Skip the prompt with:
#   --source bundled   |   --source C:\tools\enterprise-sdd-kit   |   --source git+https://…@v0.1.5
cd loan-origination
ekit doctor
git add -A; git commit -m "chore: enterprise SDD landing zone (ekit)"
opencode
```

**Existing repository (brownfield):**

```powershell
cd C:\work\existing-app
git status                  # start from a clean working tree
ekit adopt --stack springboot-vanilla --force
#   --force lets Spec Kit initialise into a non-empty folder
ekit doctor
git add -A; git commit -m "chore: adopt enterprise SDD kit (ekit)"
opencode
```

Then, inside OpenCode, **once per project**:

```text
/speckit.constitution          ratify the constitution (principles I–VIII are fixed)
/speckit.esdlc.baseline        greenfield: builds the skeleton; brownfield: gap assessment
```

Back in PowerShell:

```powershell
ekit run install               # creates .venv / node_modules from the lockfiles
ekit gate baseline             # must pass before feature work
git add -A; git commit -m "chore: landing zone and baseline conformance"
```

### D. Once per BRD

In OpenCode:

```text
/speckit.esdlc.brd docs/inbox/Loan-BRD-v3.docx     # creates docs\requirements\<slug>\
```

If the product manager is in the session, also in OpenCode:

```text
/speckit.esdlc.questions
```

If the product manager is not in the session, in PowerShell:

```powershell
ekit questions list
ekit questions export          # -> docs\requirements\<slug>\questions-for-review.csv
```

Email the CSV. When it comes back with answers:

```powershell
ekit questions import C:\Users\me\Downloads\questions-for-review.csv
ekit gate ready                # must pass before specifying features of this PRD
```

Then run `/speckit.esdlc.questions` once more in OpenCode so the answers are carried into
`prd.md`.

### E. Once per feature (repeat for each `FEAT-xx` in the PRD)

In OpenCode, in this order. Each command runs its own gate and stops if the gate fails.

| # | Slash command | Gate it enforces |
|---|---|---|
| 1 | `/speckit.specify FEAT-01` | `ready` before, `spec` after |
| 2 | `/speckit.esdlc.gherkin` | `scenarios` |
| 3 | `/speckit.clarify` *(optional)* | — |
| 4 | `/speckit.plan` | `spec` + `scenarios` before, `plan` after |
| 5 | `/speckit.tasks` | `plan` before |
| 6 | `/speckit.esdlc.red` | `red` (records the ledger) |
| — | **commit the tests and the ledger** (PowerShell, see below) | |
| 7 | `/speckit.implement` | `red-recorded` before, `green` after |
| — | **commit the code** (PowerShell, see below) | |

The commit after step 6:

```powershell
git add -A; git commit -m "test(001): red"
```

**After step 6 the red tests are frozen.** `ekit gate red` adds deny rules to `opencode.json` so the agent's edit tools cannot change that feature's `.feature` files or bound test modules (`ekit status` shows `frozen = yes`). Commit `opencode.json` and `.ekit/freeze.yaml` with the tests, then **quit and relaunch OpenCode** so the rules apply before `/speckit.implement`. If a test really is wrong, a human lifts the freeze:

```powershell
ekit unfreeze 001-user-admin --reason "step wording typo, JIRA-123"   # audited in .ekit/freeze.yaml
# put the code back to stubs, fix the test, then:
ekit gate red                                                         # new fingerprints, frozen again
```

The rules cover the agent's edit tools, not shell commands; `ekit gate green` fails if a frozen file changed anyway.

The commit after step 7:

```powershell
git add -A; git commit -m "feat(001): green"
```

In PowerShell, before opening a pull request:

```powershell
ekit gate all --feature 001-online-application
ekit gate green --format junit --out reports\gate-green.xml   # attach to the PR / feed to CI
```

For CI, run the same gate with the pin enforced, so a runner with another CLI cannot produce a verdict:

```powershell
$env:EKIT_REQUIRE_PINNED_CLI = "1"
ekit gate green --format junit --out reports\gate-green.xml
```

Install the CLI in the pipeline from the tag the lock names (`ekit.version` in `.ekit/kit.lock.yaml`).

### F. Daily / as needed

```powershell
ekit run install               # after cloning, pulling dependency changes, or changing .python-version
                               # (Python: creates/refreshes .venv from uv.lock; React: npm ci)
ekit status                    # PRDs, open questions, per-feature gate state, frozen yes/--
ekit gate <id>                 # recheck one stage: intake | ready | spec | scenarios | plan | baseline | red | red-recorded | green
ekit run lint                  # also: unit | acceptance | coverage | sca | typecheck | format | install
ekit context --nfr feature     # see the NFRs and stack rules the agent is following
```

### G. Occasionally

```powershell
ekit doctor                    # after changing tools, or when something behaves oddly
ekit upgrade                   # pull a newer kit from the pinned source
ekit upgrade --source git+https://…@v0.2.0   # switch to a different version or source
ekit sync                      # re-apply the pinned kit (e.g. after a Spec Kit upgrade)
ekit freeze [feature]           # re-apply edit protection for a red feature (gate red does this)
ekit unfreeze [feature] --reason "..."   # lift it so a wrong red test can be fixed; audited
```

Commit after `upgrade` or `sync`.

**Relaxing a gate check** (rare, and reviewed in the PR): edit
`.ekit\policy.overrides.yaml`. Every entry needs a `reason`, `approved_by` and `expires`;
an entry missing one of them, or past its expiry, is ignored and the gate report says so.

### Frequency summary

| Frequency | Commands |
|---|---|
| Once per machine | `uv tool install`, `uv tool update-shell`, `ekit doctor` |
| Per kit release | `uv tool install --force git+…@<tag>`, then per project `ekit upgrade` + commit `.ekit/`; everyone (and CI) installs the same tag |
| Once per project | `ekit init` / `ekit adopt`, `/speckit.constitution`, `/speckit.esdlc.baseline`, `ekit run install`, `ekit gate baseline` |
| Per BRD | `/speckit.esdlc.brd`, `/speckit.esdlc.questions` or `ekit questions export/import`, `ekit gate ready` |
| Per feature | specify → gherkin → plan → tasks → red → *commit, restart OpenCode* → implement → *commit* → `ekit gate all` |
| Daily | `ekit status`, `ekit gate <id>`, `ekit run <cmd>`; `ekit run install` after clone/pull of dependency changes |

## 4. Working without the kit

Plain Spec Kit remains available. Use your original commands in a separate folder:

```powershell
# New project, no kit
specify init plain-project --integration opencode
cd plain-project; opencode

# Existing project, no kit
specify init .
specify integration install opencode
opencode
```

Inside OpenCode, use the core flow:

```text
/speckit.constitution
/speckit.specify <feature description>
/speckit.clarify
/speckit.plan
/speckit.tasks
/speckit.implement
```

To turn the kit off in a project that already has it:

```powershell
specify preset remove enterprise-baseline
specify extension remove esdlc
```

Then delete the `<!-- ekit:begin -->…<!-- ekit:end -->` block from `AGENTS.md`. The
`.ekit\` folder can stay; nothing reads it unless you run `ekit`.

## 5. Benchmarking: kit vs. no kit

The goal is to compare the two ways of working on the **same BRD**, under the **same
conditions**, and measure the outcomes that matter to an enterprise: correctness,
traceability, NFR coverage, rework and cost.

### 5.1 Set-up rules (fairness)

1. **Same input:** one real but small BRD, about 2–4 features.
2. **Same model and settings in OpenCode** for both arms, and the **same ekit CLI version** for every
   kit run (and for scoring Arm A in 5.4). Record it: a different CLI can judge the same artifacts differently.
3. **Same person driving**, or two people of similar experience, one per arm.
4. **Fresh repositories** for each run, created from the same starting commit.
5. **Hold-out acceptance tests.** Before either arm starts, someone who will not drive
   either arm writes an independent acceptance test pack from the BRD (black-box API/UI
   tests). Neither arm sees it. It is the referee.
6. **Repeat each arm at least 3 times.** LLM output varies between runs, so a single run
   proves nothing. Compare medians.
7. **Answer business questions identically.** Keep a "business oracle" sheet of answers the
   product manager has agreed. In the no-kit arm, answer only when the agent asks. In the
   kit arm, answer through the questions register. Record how many questions each arm raised.

### 5.2 Create the two arms

```powershell
# Arm A: no kit (repeat for run 1..3)
specify init bench-plain-r1 --integration opencode

# Arm B: with kit (repeat for run 1..3)
ekit init bench-ekit-r1 --stack fastapi-react --source bundled
```

Use the same stack in both. For Arm A, put the stack choice in the first
`/speckit.specify` prompt so the agent is not choosing a different stack.

### 5.3 Metrics and how to collect them

| # | Metric | How to measure | Better |
|---|---|---|---|
| M1 | **Functional correctness** | % of hold-out acceptance tests passing at "done" | higher |
| M2 | **Defects after done** | hold-out failures + bugs found in a 30-min exploratory test | lower |
| M3 | **Business questions surfaced** | count of distinct ambiguities raised *before* coding (Arm B: `open-questions.yaml`; Arm A: questions asked in chat) | higher (up to the real number) |
| M4 | **Wrong guesses** | business rules implemented differently from the oracle sheet without asking | lower |
| M5 | **NFR coverage** | score both repos against the NFR catalogue: run `ekit context --nfr all` and tick each NFR *Met / Partially / Not met* by reading the code (same reviewer for both) | higher |
| M6 | **Traceability** | % of acceptance criteria that can be traced to a test that checks them (see 5.4) | higher |
| M7 | **Test-first evidence** | Arm B: ledger entries; Arm A: `git log` shows tests committed before code? (yes/no per feature) | yes |
| M8 | **Lead time** | wall-clock from BRD received to all features "done" (note start/end times) | lower, but read together with M1–M6 |
| M9 | **Human interventions** | number of times you had to correct, redirect or re-prompt the agent | lower |
| M10 | **Rework** | lines changed after first "done" until the hold-out tests pass: `git diff --stat <done-commit> HEAD` | lower |
| M11 | **Cost** | tokens / spend per arm, from your model provider's usage dashboard (or OpenCode's usage stats, if your version shows them) | lower, but read together with M1–M6 |
| M12 | **Coverage & static checks** | run the same coverage, lint and dependency-audit commands in both repos | higher coverage, fewer findings |

Expect the kit to cost more in M8 and M11 (more steps, more tokens). The question the
benchmark answers is whether that buys enough in M1–M7, M9 and M10.

### 5.4 Scoring a no-kit repo with the kit's own gates (optional)

You can use the gates as a measuring tool on Arm A without changing Arm A itself. Work on
a **copy**:

```powershell
Copy-Item -Recurse C:\work\bench-plain-r1 C:\work\bench-plain-r1-scored
cd C:\work\bench-plain-r1-scored
ekit adopt --stack fastapi-react --source bundled --force --non-interactive
ekit gate all --format json --out reports\score.json
```

Arm A will lack most artifacts: no PRD, no `trace.yaml`, no `@SCN` tags, no conformance
tables. Gate failures there mostly measure **missing artifacts** rather than code quality.
Use this result to quantify the gaps for M5/M6, not as the headline score. M1 from the
hold-out tests is the headline.

### 5.5 Results sheet

Record one row per run in a spreadsheet (`benchmark.csv`):

```text
arm,run,brd,model,ekit_cli,kit_version,features,lead_time_min,interventions,questions_raised,wrong_guesses,holdout_pass_pct,defects_after_done,nfr_met_pct,ac_traced_pct,test_first(y/n),rework_lines,coverage_pct,lint_findings,sca_high,tokens,cost
plain,1,loan-v3,<model>,-,-,3,,,,,,,,,,,,,,,
ekit,1,loan-v3,<model>,0.1.5,0.1.6,3,,,,,,,,,,,,,,,
```

Compare the **median of each arm**. Report deltas for M1, M2, M4, M5, M6 and M10 first,
then cost and time.

### 5.6 Decision rule (suggested)

Adopt the kit as the default if, across 3+ runs, all of these hold:

- hold-out pass rate (M1) is equal or better;
- wrong guesses (M4) and defects after done (M2) are lower;
- NFR coverage (M5) and traceability (M6) are clearly higher;
- the extra lead time and cost stay within what you would spend fixing those gaps manually.

## 6. Troubleshooting on Windows

| Symptom | Likely cause | Fix |
|---|---|---|
| `ekit` not recognized | uv tools folder not on PATH | `uv tool update-shell`, then open a new terminal |
| `Spec Kit CLI specify not found` | `specify` not on PATH for this shell | reinstall with `uv tool install specify-cli`, or set `$env:EKIT_SPECIFY = "C:\path\to\specify.exe"` |
| Slash commands missing in OpenCode | OpenCode started outside the project root, or not restarted after `ekit sync` | `cd` to the root and restart `opencode` |
| `Cannot tell which feature to check` | not on the `NNN-name` branch | `git switch 001-…`, or add `--feature 001-…` |
| `Cannot tell which PRD to check` | more than one PRD folder | add `--prd docs/requirements/<slug>` |
| `kit integrity` fails in `ekit doctor` | someone edited `.ekit\kit\` | revert those files, or run `ekit upgrade` |
| `ekit doctor`: "ekit CLI matches the project pin" fails | you run a different CLI version than the one in `.ekit/kit.lock.yaml` | install the pinned tag: `uv tool install --force git+https://…/sdd-kit.git@v<pinned>`; or, as a reviewed change for the whole team, `ekit upgrade` and commit `.ekit/` |
| Teammates or CI get a different gate result for the same commit | different ekit CLI versions (check logic differs), or `.ekit/` changes not committed | compare `ekit --version`; `git status .ekit`; see *What is pinned, and what is not* |
| Gate exits 2: "EKIT_REQUIRE_PINNED_CLI is set …" | CI runner installed another CLI than the pin | install the CLI tag named in the lock in the pipeline |
| "Kit … requires ekit >=0.1.5,<0.2 … (not <0.2)" | your CLI is newer than the kit allows | install a CLI in the allowed range, or upgrade the project to a kit that allows your CLI |
| "kit.lock.yaml does not record an ekit CLI version" | project vendored by ekit < 0.1.4 | run `ekit upgrade` once with the team's CLI and commit `.ekit/` |
| `red`: "produced no report" | BDD runner not wired, or doesn't compile yet | run `ekit run acceptance` and read the error; the report path is in `ekit context` |
| `red`: "PASSES before implementation" | the test doesn't check the new behaviour | strengthen the assertion. Don't change the gate |
| `red`: "skipped — red needs the scenario to run and FAIL" | a `@skip`/`@wip` tag, a skip marker, or a tag filter in the runner config excludes the scenario | remove the skip or filter; a skipped scenario is not evidence that the test can fail |
| `green`: "never recorded failing (red) before green" after upgrading to 0.1.5 | the red ledger recorded `skipped`, not `failed` | `ekit unfreeze <feature> --reason "…"`, put the code back to stubs, `ekit gate red` |
| Gate note: "override for … ignored: `approved_by`, `expires` required" | override written for ekit < 0.1.5 | add the approver and an expiry date, or remove the override |
| `plan`/`baseline`: "Waived requires an ADR reference" although a date is given | since 0.1.5 a date is not an ADR reference | create the ADR in `docs/adr/` and cite `ADR-NNNN` |
| `ready`: "blocking question answered without `answered_by`" | the decision has no named owner | record who decided in `open-questions.yaml`, or re-import the CSV with `answered_by` filled |
| Maven wrapper errors | `JAVA_HOME` not set or not JDK 21 | set `JAVA_HOME`, then open a new terminal |
| `npm` step fails with path errors | Windows long-path limit | `git config --global core.longpaths true`; enable Win32 long paths |
| `BASE-ENV`: "uses Python 3.x but .python-version pins 3.y" | venv was created with another interpreter | `Remove-Item -Recurse -Force .venv`, then `ekit run install` |
| `BASE-ENV`: ".venv/ has files committed" | the venv was accidentally committed | `git rm -r --cached .venv`, then commit |
| `uv run --locked` fails with "lockfile needs to be updated" | `pyproject.toml` changed without re-locking | `uv lock`, review the diff, commit `uv.lock` |
| CSV opens with garbled characters | file was re-saved in a different encoding | keep it as *CSV UTF-8* when saving from Excel |
