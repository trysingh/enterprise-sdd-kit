# ekit on Windows: Runbook and Benchmark Guide

This guide covers running the Enterprise SDD Kit (`ekit`) on Windows when GitHub Spec Kit
(`specify`) and OpenCode already work on the machine. It also explains how to measure the
kit against plain Spec Kit.

> **Status:** ekit 0.3.0 / kit 0.3.0. The MVP1 pipeline is verified on Linux against Spec Kit 1.2.7 and has
> run on Windows with FastAPI + pytest-bdd against a real project; that project found every gap fixed in
> 0.2.1–0.2.5. 0.3.0 adds the **golden landing zone** for `fastapi-jinja` and structural fixes for those gaps
> (see *C*, *K*, and `docs/design/0.3.0-golden-landing-zone.md`). Waves, model tiers and every release since
> 0.2.2 are covered by unit and CLI tests but have not yet run against a live Spec Kit + OpenCode install. The
> golden application itself has not been run yet either; the first golden project is the pilot (see *K*).

## 1. Dependencies and assumptions

### Required on the machine

| Dependency | Version | Needed for | Check with |
|---|---|---|---|
| Windows | 10 / 11 | — | — |
| PowerShell | 7.x recommended (5.1 works) | running commands | `$PSVersionTable.PSVersion` |
| Git for Windows | 2.40+ | kit from git, ledger commit tracking, feature-branch detection | `git --version` |
| uv | 0.5+ | installing `ekit`; Python stacks | `uv --version` |
| Python | 3.11+ (uv can provide it) | running `ekit` and Spec Kit's Python scripts | `python --version` |
| Spec Kit CLI (`specify`) | 1.0+ (tested 1.2.7) | everything | `specify version` |
| OpenCode | current, with a model provider configured | running the slash commands | `opencode --version` |

### Required per stack

| Stack | Additional dependencies |
|---|---|
| `fastapi-jinja` | none beyond uv/Python. The golden landing zone (0.3.0, the default for this stack) runs `uv lock` once on install, which needs network access to PyPI or your package index |
| `fastapi-react` | Node.js 20 LTS+ and npm |
| `springboot-vanilla` | JDK 21 with `JAVA_HOME` set (the Maven wrapper is generated by the landing-zone step, so no global Maven is needed) |
| `springboot-react` | JDK 21 + `JAVA_HOME`, Node.js 20 LTS+ and npm |
| Any `@ui` (browser) scenario | Playwright browsers, installed by the landing-zone step |

### Assumptions the commands rely on

1. `ekit`, `specify`, `opencode`, `git` and `uv` are on `PATH` in the terminal you use.
   After installing ekit, run `uv tool update-shell` once and open a new terminal.
2. You run `ekit` commands from the project root, or any folder below it. ekit finds the
   project by looking upward for `.ekit\project.yaml`.
3. Feature work happens on the branch Spec Kit creates (`001-feature-name`). ekit uses that
   branch name to find the active feature. If you are not on the branch, add
   `--feature 001-feature-name`, or set the environment variable:
   `$env:SPECIFY_FEATURE = "001-feature-name"`.
4. One PRD per folder under `docs\requirements\<slug>\`. If there is more than one PRD, pass
   `--prd docs/requirements/<slug>` to `intake`, `ready` and `questions`.
5. Everything ekit creates gets committed, including `.ekit\` with `kit.lock.yaml`,
   `ledger\` and `policy.overrides.yaml` (and, if you use them, `waves.yaml` and `models.yaml`).
   The ledger is the evidence that tests failed (red) before the code made them pass (green).
6. Do not edit files in `.ekit\kit\` by hand. Change the kit at its source and run
   `ekit upgrade`. `ekit doctor` flags local edits. To give the agent more detail for your
   project or for yourself, use the places in *H. Adding your own guidance for the agent*;
   none of them are hashed, so they never cause an integrity failure.
7. Long paths (relevant for `node_modules`): run
   `git config --global core.longpaths true` once. If Windows still complains, enable
   *Win32 long paths* in Group Policy or the registry.
8. **Python environments are project-local (ENV-01).** Python stacks always use a `.venv`
   in the backend folder, created by uv from `uv.lock`, and pinned by `.python-version`.
   - You never activate it. `ekit run …` and the agents call `uv run --locked`, which uses
     `.venv\Scripts\python.exe` automatically.
   - Never `pip install` into the global Python.
   - After cloning a project, run `ekit run install` once.
   - If uv doesn't find the pinned Python on the machine, it downloads it.

   React uses a local `node_modules` (`npm ci`, `.nvmrc`). Spring Boot uses the Maven
   wrapper. `ekit gate baseline` and `ekit gate green` fail if an environment folder is
   committed, isn't in `.gitignore`, or doesn't match its pinned version.
9. Line endings don't matter. The kit hash ignores CRLF vs LF, so `core.autocrlf=true`
   is fine.
10. **Everyone runs the same ekit CLI version.** The rules are pinned in the repository, but the
    CLI that applies them is installed per machine. The project records the agreed CLI version in
    `.ekit\kit.lock.yaml`; install exactly that tag. See *What is pinned, and what is not* below.

### What is pinned, and what is not

| Part | Where it lives | Pinned by | Changes when |
|---|---|---|---|
| **Rules**: gate policy, NFR catalogue, stack profiles, templates, agent rules | `.ekit/kit/` in the repository (committed) | `.ekit/kit.lock.yaml`: source, resolved commit, sha256 | someone runs `ekit upgrade` and commits the result |
| **Check engine**: the `ekit` CLI that reads those rules and judges the files (`checks.py`, `gates.py`, step scan, fingerprints) | each machine's uv tool folder | `ekit.version` in `.ekit/kit.lock.yaml` (since ekit 0.1.4), plus the kit's allowed range `requires.ekit` (e.g. `>=0.3.0,<0.4`) | a developer reinstalls the CLI |
| **Project guidance**: ratified constitution, `AGENTS.md` outside the ekit block | `.specify\memory\constitution.md`, `AGENTS.md` (committed) | not pinned or hashed; reviewed in pull requests | anyone edits them (see *H*) |
| **Personal guidance** | `$HOME\.config\opencode\AGENTS.md` (your machine only) | not pinned; never in the repository | you edit it |
| **Wave plan** (optional) | `.ekit/waves.yaml` (approved, committed); proposal in `docs/planning/waves.proposed.yaml` | `approved_by` and history inside the file; only `ekit wave approve` / `advance` write it | a person approves or advances (see *I*) |
| **Model routing** (optional) | `.ekit/models.yaml` (committed); `model:` lines in `.opencode/commands/*.md` | the kit's tier table (`policy/models.policy.yaml`) plus your tier → model choice | a person runs `ekit models setup` (see *J*) |

Both of the first two parts decide a gate result. Identical rules judged by two different CLI versions can disagree,
because check logic changes between releases (0.1.1 changed how tags are read, 0.1.2 added
`RED-STEPS-ASSERT` and `GREEN-TESTS-UNCHANGED`, 0.1.5 stopped counting skipped scenarios as red, 0.2.1 added
`RED-STEPS-BOUND` and the committed-evidence checks). Project and
personal guidance shape what the agent tries; they never change what a gate accepts. The wave plan does change
what a gate accepts (scope, deferrals, active profiles), which is why only a person can approve it. So:

- **One CLI version per project.** `ekit init` and `ekit upgrade` record the running CLI version in the lock.
  Everyone, and CI, installs exactly that version.
- **Install by tag.** Tag the kit repository with the CLI version (e.g. `v0.3.0`; one tag then fixes both the CLI
  and the kit it ships) and install it with `uv tool install --force git+https://…/sdd-kit.git@v0.3.0`.
- **Mismatch is visible.** `ekit doctor` fails the row *ekit CLI matches the project pin*, `ekit status` prints a
  `!!` line, and every gate report (text, JSON and JUnit) carries a note naming both versions.
- **CI refuses to judge with the wrong CLI.** Set `EKIT_REQUIRE_PINNED_CLI=1` in the pipeline: a gate then exits 2
  before running any check if the installed CLI differs from the pin.
- **Moving the team to a new CLI is a reviewed change.** Install the new CLI, run `ekit upgrade` (re-vendors the
  kit and re-pins the CLI), commit `.ekit/`, and have everyone reinstall the same tag after the merge.
- **`bundled` couples the two.** With `--source bundled`, `ekit upgrade` vendors the kit shipped inside the CLI you
  are running, so whoever upgrades also chooses the kit version. Teams should prefer a git source pinned to a tag.
- **Evidence names its judge.** Every red and green ledger entry records `ekit_version` next to `kit_version`.

Check what you run before comparing gate results with anyone: `ekit --version`, then `ekit doctor`.

## 2. Where and how to launch

| What | Where | How |
|---|---|---|
| `ekit ...` commands | **Windows Terminal / PowerShell**, in the project root | normal CLI |
| `/speckit.*` slash commands | **inside OpenCode**, started from the project root | `cd C:\work\my-project` then `opencode` |
| Gates (`ekit gate ...`) | either place. OpenCode runs them itself as part of each slash command; you can also run them in PowerShell to check state | — |

Two windows side by side work well: OpenCode on the left, PowerShell on the right for
`ekit status` and `ekit gate ...`.

> Always launch OpenCode from the **project root**. It reads `AGENTS.md`,
> `.opencode\commands` and `.opencode\agents` from there. If you start it elsewhere, the
> slash commands and rules won't load.

## 3. Commands by frequency

### A. Once per machine

```powershell
# 1. Unzip the kit somewhere permanent
Expand-Archive "$HOME\Downloads\enterprise-sdd-kit.zip" -DestinationPath C:\tools

# 2. Install the ekit CLI and put uv tools on PATH
uv tool install C:\tools\enterprise-sdd-kit
uv tool update-shell        # then open a NEW terminal

# 3. Git settings (if not already set)
git config --global core.longpaths true

# 4. Verify
ekit --version
ekit stacks
ekit doctor                 # outside a project it checks tools only
```

Optional, to make your team's kit the default source for every `init`:

```powershell
[Environment]::SetEnvironmentVariable("EKIT_KIT_SOURCE", "git+https://git.example.com/eng/sdd-kit.git@v0.3.0", "User")
# use the same tag for the CLI itself:
uv tool install --force git+https://git.example.com/eng/sdd-kit.git@v0.3.0
```

Optional, personal rules for the agent in every project on this machine (see *H*):

```powershell
New-Item -ItemType Directory -Force "$HOME\.config\opencode" | Out-Null
notepad "$HOME\.config\opencode\AGENTS.md"
```

### B. When the kit itself changes (new kit version)

```powershell
# Reinstall the CLI from the new tag (preferred) or the updated folder
uv tool install --force git+https://git.example.com/eng/sdd-kit.git@v0.3.0
# or: uv tool install --force C:\tools\enterprise-sdd-kit
ekit --version
```

Projects do **not** change automatically, and until they do, `ekit doctor` reports that your CLI no
longer matches their pin. Move a project deliberately, as one reviewed change:

```powershell
cd C:\work\loan-origination
ekit upgrade                      # re-vendors the kit and re-pins the CLI version in kit.lock.yaml
ekit doctor
git add .ekit; git commit -m "chore: ekit 0.3.0 / kit 0.3.0"
```

`ekit upgrade` rewrites only the ekit block in `AGENTS.md` and never touches a ratified constitution, so project
principles (IX+) and your own `AGENTS.md` text survive the upgrade.

After the merge, everyone on the project (and the CI image) installs the same tag. Until then, keep
the previous CLI for projects that have not moved: `uv tool install --force git+…@v<previous>`.

### C. Once per project

**New `fastapi-jinja` project with the golden landing zone (0.3.0; the default for this stack):**

```powershell
cd C:\work
ekit init loan-origination --stack fastapi-jinja --name "Loan Origination"
#   installs the kit's pre-built landing zone, ratifies the constitution (no model involved),
#   runs `uv lock` once (network), and freezes the golden core against agent edits.
#   --baseline generate opts out (then follow "any other stack" below).
cd loan-origination
ekit run install               # .venv from uv.lock
ekit run unit; ekit run acceptance       # the golden core's own tests and the 000-* scenarios: all green
ekit gate baseline             # passes on a fresh golden install; records .ekit/ledger/baseline.yaml
git add -A; git commit -m "chore: golden landing zone (ekit)"
ekit baseline status           # golden revision, frozen core, drift, seams
opencode
```

There is no `/speckit.constitution` or `/speckit.esdlc.baseline` step to run. Use `/speckit.constitution`
only to add project principles IX and above (*H*). Go straight to *D*. If `uv lock` could not run during
`ekit init` (no network, no uv on PATH), `ekit gate baseline` fails with `missing uv.lock`: run `uv lock`
once, then `ekit run install`.

**New project, any other stack (greenfield, generated landing zone):**

```powershell
cd C:\work
ekit init loan-origination --stack fastapi-react
#   asks for the kit source (bundled / local folder / git). Skip the prompt with:
#   --source bundled   |   --source C:\tools\enterprise-sdd-kit   |   --source git+https://…@v0.3.0
cd loan-origination
ekit doctor
git add -A; git commit -m "chore: enterprise SDD landing zone (ekit)"
opencode
```

**Existing repository (brownfield):**

```powershell
cd C:\work\existing-app
git status                  # start from a clean working tree
ekit adopt --stack springboot-vanilla --force
#   --force lets Spec Kit initialise into a non-empty folder
ekit doctor
git add -A; git commit -m "chore: adopt enterprise SDD kit (ekit)"
opencode
```

Optional: to run the flagship-tier steps below on your flagship model, set up model tiers first with
`ekit models setup` (see *J*), commit, and restart OpenCode.

Then, inside OpenCode, **once per project** (generated landing zone; golden projects skip this):

```text
/speckit.constitution          ratify the constitution (principles I–VIII are fixed; project principles go in IX+, see H)
/speckit.esdlc.baseline        greenfield: builds the skeleton; brownfield: gap assessment
```

Back in PowerShell:

```powershell
git diff .specify/memory/constitution.md   # only placeholders, version/dates and IX+ should have changed
ekit run install               # creates .venv / node_modules from the lockfiles
ekit gate baseline             # must pass before feature work; records .ekit/ledger/baseline.yaml
git add -A; git commit -m "chore: landing zone and baseline conformance"
ekit status                    # Landing zone: baseline: passed — <date> at <commit>
```

Run `git init` before the landing zone if the folder is not a repository yet: ekit needs git to verify
that environment folders are ignored, and the red/green evidence is checked against commits.

### D. Once per BRD

In OpenCode:

```text
/speckit.esdlc.brd docs/inbox/Loan-BRD-v3.docx     # creates docs\requirements\<slug>\
```

If the product manager is in the session, also in OpenCode:

```text
/speckit.esdlc.questions
```

If the product manager is not in the session, in PowerShell:

```powershell
ekit questions list
ekit questions export          # -> docs\requirements\<slug>\questions-for-review.csv
```

Email the CSV. When it comes back with answers:

```powershell
ekit questions import C:\Users\me\Downloads\questions-for-review.csv
ekit gate ready                # must pass before specifying features of this PRD
```

Then run `/speckit.esdlc.questions` once more in OpenCode so the answers are carried into
`prd.md`.

At the end of `/speckit.esdlc.brd` the agent asks **once** whether to deliver the product in waves. Answer in
chat, then run the matching command yourself in PowerShell (the agent is not allowed to): `ekit wave init`
to plan in waves (see *I*), or `ekit wave decline`. If waves are already on, a new or changed BRD's
acceptance criteria must be placed in a wave and approved before they can be specified.

### E. Once per feature (repeat for each `FEAT-xx` in the PRD)

In OpenCode, in this order. Each command runs its own gate and stops if the gate fails. With waves on, a
feature here is a **wave slice**: `/speckit.specify FEAT-02` includes only the ACs `ekit wave scope FEAT-02` lists
for the current wave, and a later slice of the same PRD feature becomes a new feature folder (e.g.
`011-loan-application-w2`).

| # | Slash command | Gate it enforces |
|---|---|---|
| 1 | `/speckit.specify FEAT-01` | `ready` before, `spec` after |
| 2 | `/speckit.esdlc.gherkin` | `scenarios` |
| 3 | `/speckit.clarify` *(optional)* | — |
| 4 | `/speckit.plan` | `spec` + `scenarios` before, `plan` after |
| 5 | `/speckit.tasks` | `plan` before |
| 6 | `/speckit.esdlc.red` | `red` (records the ledger) |
| — | **commit the tests and the ledger** (PowerShell, see below) | |
| 7 | `/speckit.implement` | `red-recorded` before, `green` after |
| — | **commit the code** (PowerShell, see below) | |

**Which feature?** `/speckit.esdlc.red` and `/speckit.implement` no longer decide this themselves. They run
`ekit feature current --for red|implement "<what you typed>"`, which prints one real feature folder or fails
with the list of real ones. Pass the feature explicitly (`/speckit.implement 003`) when several are in flight.
You can run the same command in the terminal.

**Golden projects (0.3.0):**
- All of a feature's code goes in its own package: `ekit feature package 003-chat` prints
  `src/app/features/f003_chat`.
- The red step creates that package with `not_implemented()` stubs (a 501 problem document), registers its
  router in `src/app/features/registry.py`, and writes the step module as
  `tests/acceptance/test_003_chat.py`.
- Steps reuse the shared ones in `tests/acceptance/conftest.py` and keep state on `ctx: ScenarioContext`.
- The reference slice (`specs/000-reference-slice/`) is the model to copy. Red and green reject a feature
  that uses it (`RED-`/`GREEN-NO-EXEMPLAR`).
- Edits to the golden core are refused by OpenCode, and green fails if one gets through anyway
  (`GREEN-GOLDEN-INTACT`).

The commit after step 6, **before** `/speckit.implement`. It must contain the feature files under `specs/`, the bound
tests, `.ekit/ledger/`, `.ekit/freeze.yaml`, `opencode.json` and, for the first feature of a PRD,
`docs/requirements/<slug>/`. `ekit gate red-recorded` and `ekit gate green` fail (`REDREC-COMMITTED`,
`GREEN-RED-COMMITTED`) until the files recorded at red are committed exactly as recorded:

```powershell
git add -A; git commit -m "test(001): red"
git status --short             # nothing under specs/ or tests/ should be left untracked
```

**After step 6 the red tests are frozen.** `ekit gate red` adds deny rules to `opencode.json` so the agent's edit tools cannot change that feature's `.feature` files or bound test modules (`ekit status` shows `frozen = yes`). Commit `opencode.json` and `.ekit/freeze.yaml` with the tests, then **quit and relaunch OpenCode** so the rules apply before `/speckit.implement`. If a test really is wrong, a human lifts the freeze:

```powershell
ekit unfreeze 001-user-admin --reason "step wording typo, JIRA-123"   # audited in .ekit/freeze.yaml
# put the code back to stubs, fix the test, then:
ekit gate red                                                         # new fingerprints, frozen again
```

Since 0.2.2, `ekit unfreeze` also denies the feature's production source directory by default for as long as
it stays unfrozen (not just the test files) — the point of unfreezing is to fix the test, and an agent that
uses the window to implement production code instead has repeated the mistake the freeze exists to catch.
`ekit gate red` lifts that source-deny again the moment it re-freezes. Pass `--allow-src` to skip this (rare —
mainly if you genuinely want to keep implementing while you fix the test).

The rules cover the agent's edit tools, not shell commands; `ekit gate green` fails if a frozen file changed anyway.

**Since 0.2.3**, `ekit fix-red` automates that whole unfreeze/fix-glue cycle in one reviewed command, for the
case where the implementation is already committed (so there's nothing for a stash to grab):

```powershell
ekit fix-red 001-user-admin --reason "step wording typo, JIRA-123"
# unfreezes, checks the production source back to the commit recorded as this feature's last red,
# runs `ekit gate red`, then restores the production source either way — it never commits.
```

If the report it prints still isn't clean, fix the test glue further and run it again; once it is, review the
test diff and commit yourself, same as step 6 above. It's denied to the agent's shell tool, same as
`ekit unfreeze` — a person decides this, not the agent.

If the failure it reports isn't a plain `AssertionError`, read the message `ekit fix-red` prints: the revert is
scoped to the feature's whole production source directory, which on a project with more than one feature
sharing that directory can reach back further than this particular fix needs. The message explains the
narrower, manual alternative (revert just the specific file(s) by hand) for that case.

The commit after step 7:

```powershell
git add -A; git commit -m "feat(001): green"
```

In PowerShell, before opening a pull request:

```powershell
ekit gate all --feature 001-online-application
ekit gate green --format junit --out reports\gate-green.xml   # attach to the PR / feed to CI
```

For CI, run the same gate with the pin enforced, so a runner with another CLI cannot produce a verdict:

```powershell
$env:EKIT_REQUIRE_PINNED_CLI = "1"
ekit gate green --format junit --out reports\gate-green.xml
```

Install the CLI in the pipeline from the tag the lock names (`ekit.version` in `.ekit/kit.lock.yaml`).

### F. Daily / as needed

```powershell
ekit run install               # after cloning, pulling dependency changes, or changing .python-version
                               # (Python: creates/refreshes .venv from uv.lock; React: npm ci)
ekit status                    # PRDs, open questions, per-feature gate state, frozen yes/--
ekit gate <id>                 # recheck one stage: intake | ready | spec | scenarios | plan | baseline | red | red-recorded | green
ekit run lint                  # also: unit | acceptance | coverage | sca | typecheck | format | install
ekit context --nfr feature     # see the NFRs and stack rules the agent is following
```

### G. Occasionally

```powershell
ekit doctor                    # after changing tools, or when something behaves oddly
ekit upgrade                   # pull a newer kit from the pinned source
ekit upgrade --source git+https://…@v0.3.0   # switch to a different version or source
ekit sync                      # re-apply the pinned kit (e.g. after a Spec Kit upgrade)
ekit freeze [feature]           # re-apply edit protection for a red feature (gate red does this)
ekit unfreeze [feature] --reason "..."   # lift it so a wrong red test can be fixed; audited
ekit baseline status                    # golden: revision, freeze state, drift, seams
ekit adr new "Title"                    # next free ADR number (the agent uses it too)
```

Commit after `upgrade` or `sync`.

**Relaxing a gate check** (rare, and reviewed in the PR): edit
`.ekit\policy.overrides.yaml`. Every entry needs a `reason`, `approved_by` and `expires`;
an entry missing one of them, or past its expiry, is ignored and the gate report says so.

### H. Adding your own guidance for the agent

You can give the agent more detail for your use case (domain terms, conventions, worked examples,
personal preferences) without touching anything ekit pins. None of the places below is hashed or
read by a gate, so additions never cause a SHA or integrity failure. Choose by who should see it:

| Put it in | Who sees it | Which tool provides it | Use it for |
|---|---|---|---|
| `.specify\memory\constitution.md`, principle **IX and above** | the whole team (committed) | **Spec Kit**: the constitution file and `/speckit.constitution`. **ekit** seeds principles I–VIII into it via the `enterprise-baseline` preset | project-wide principles, e.g. "amounts are integer minor units, never floats" |
| `AGENTS.md`, **outside** the `<!-- ekit:begin -->…<!-- ekit:end -->` block | the whole team (committed) | **OpenCode** loads it in every session. **ekit** keeps your text when `ekit sync` / `ekit upgrade` rewrite their block | conventions, domain glossary, module map, examples of good code |
| `$HOME\.config\opencode\AGENTS.md` | only you, in every project on this machine (never in the repository) | **OpenCode** global rules, combined with the project's `AGENTS.md` | personal preferences: how much to explain, review style, naming habits |

**Add a project principle** (inside OpenCode):

```text
/speckit.constitution Add principle IX "Money as integers": store and compute amounts as integer minor units; never floats.
```

Then review and commit in PowerShell:

```powershell
git diff .specify/memory/constitution.md   # only IX+ and the version / Last Amended lines may change
git add .specify/memory/constitution.md; git commit -m "docs(constitution): add principle IX"
```

**Add project notes for the agent:** edit `AGENTS.md` below the `<!-- ekit:end -->` line (or above
`<!-- ekit:begin`), commit it, and restart OpenCode.

**Add personal rules:** edit `$HOME\.config\opencode\AGENTS.md` (for example
`C:\Users\<you>\.config\opencode\AGENTS.md`) and restart OpenCode. If the notes only matter for one
project, put them under a heading that names it. There is no per-developer, per-project file yet.
This is the first Windows run: if OpenCode doesn't pick the file up, check where your OpenCode build
keeps its global configuration and put `AGENTS.md` there.

Rules that keep this safe:

- **Add or tighten, never loosen.** A principle or note may add detail or be stricter. It cannot relax
  principles I–VIII or a gate. Relaxing a check goes through `.ekit\policy.overrides.yaml` (reason,
  approver, expiry); deferring an NFR goes through a `Waived` row with an ADR.
- **The gates decide, not the text.** Gates read the policy in `.ekit\kit\`, not the constitution or
  `AGENTS.md`. A note saying "60% coverage is fine" changes what the agent attempts, not what
  `ekit gate green` accepts.
- **Never write inside the ekit block** of `AGENTS.md`; `ekit sync` and `ekit upgrade` overwrite it.
- **Never put guidance in `.ekit\kit\`.** `ekit doctor` reports a kit-integrity failure, and the agent's
  edit tools are denied there anyway.
- **Personal rules must not contradict project rules.** OpenCode combines both files; the gates still
  judge the result.

**Principles I–VIII are checked since 0.3.0.** `ekit gate baseline` compares them, word for word
(whitespace aside), with the kit template (`BASE-CONSTITUTION`). A reworded or removed principle fails the gate.
Project principles IX and above are free. `ekit constitution ratify` fills the template's placeholders
(name, version, dates, stack) without a model; `ekit init` runs it for golden projects.
`ekit constitution check` shows the state. Changing I–VIII still needs an ADR and a new kit version. To see the full history:

```powershell
git log -p -- .specify/memory/constitution.md
```

### I. Optional: delivering in waves (several MVPs)

Off unless you turn it on. **W1** shows the overall face of the system: navigation shell, sign-in, a minimal
screen and one working happy path per major feature, on a real backend. Later waves deepen it by priority
(remaining acceptance criteria, edge cases, admin depth, deferred NFRs) and absorb new BRDs.

| Step | Who | Command |
|---|---|---|
| Start a proposal | person | `ekit wave init` → `docs/planning/waves.proposed.yaml`, every AC in W1, an empty W2 |
| Shape it | product owner, with the agent's help | edit the proposal: move ACs (`loan:AC-012`) or whole features (`loan:FEAT-03`) to later waves, add `dependencies`, add `defer` entries with `reason` and `approved_by`; optional `profiles: [backend]` for a backend-only wave |
| Check it | anyone | `ekit wave validate --proposal` |
| Approve it | person | `ekit wave approve --by "Head of Product"` |
| Work the current wave | team + agent | the feature pipeline (*E*) for each slice; `ekit wave scope FEAT-xx` shows what belongs to this wave |
| Move on | person | `ekit wave advance --by "Head of Product"` (add `--carry` to move unfinished ACs to the next wave) |
| See where things stand | anyone | `ekit wave` (or `ekit status`) |

```powershell
ekit wave init
# edit docs/planning/waves.proposed.yaml
ekit wave validate --proposal
ekit wave approve --by "Head of Product"
git add .ekit/waves.yaml docs/planning; git commit -m "plan: approve waves"
```

A minimal proposal:

```yaml
apiVersion: ekit/v1
kind: WavePlan
waves:
  - id: W1
    goal: "Face of the system"
    scope: ["loan:FEAT-01", "loan:AC-003"]          # all of FEAT-01, one AC of FEAT-02
  - id: W2
    goal: "Deepen: applications and admin"
    scope: ["loan:AC-004", "loan:FEAT-03"]
dependencies:
  "loan:FEAT-03": ["loan:FEAT-01"]                  # admin needs users first
defer:
  - {nfr: UX-01, until: W2, reason: "UI is a thin shell in W1", approved_by: "Head of Product"}
```

What the rules are:

- **Every AC of every PRD is in exactly one wave.** Approval writes the plan with explicit ACs, so an AC added
  later (a new or changed BRD) is "not in any wave" until someone places it in the proposal and approves again;
  approval lists the newly placed ACs.
- **Scope:** `ekit gate spec` fails (`SPEC-WAVE-SCOPE`) when a feature specifies an AC planned for a later wave.
- **Deferrals:** a conformance row may say `Deferred (W2)` only while W2 is still in the future and only for an
  NFR the plan defers. The NFRs in `.ekit\kit\policy\waves.policy.yaml` (authentication, authorisation, input
  validation, secrets, scanning, data classification, ENV-01, test-first, lint, ADRs) can never be deferred.
  Moving a deferral to a later wave is recorded as a re-deferral and counted in `ekit wave`.
- **Advancing** is refused while an AC of the current wave has no green feature, unless `--carry` moves it on
  (recorded). NFRs deferred to the new wave become required. A wave with `profiles: [backend]` skips the
  frontend's commands, paths, environment and BDD runs, and every gate report names what is skipped; when the
  frontend becomes active, run `ekit gate baseline` again.
- **Turning it off:** `ekit wave decline` before anything is approved. Once a plan is approved, removing
  `.ekit\waves.yaml` is a reviewed change.

Not built yet: an agent command that drafts the proposal with a reason per feature, `ekit wave move` and a CSV
round-trip for the product owner (planned for 0.2.2); change-impact analysis and a cross-wave regression gate (0.3.0).

### J. Optional: model tiers

Off unless you turn it on. The kit decides which **tier** each command runs on; you decide which **model** serves
each tier. Decisions and contracts run on the flagship model; volume work the gates check runs on the standard
model.

| Tier | Commands and agents |
|---|---|
| flagship | `/speckit.esdlc.brd`, `/speckit.constitution`, `/speckit.esdlc.baseline`, `/speckit.plan`, `/speckit.esdlc.red`; agents `requirements-analyst`, `test-author` |
| standard | `/speckit.specify`, `/speckit.clarify`, `/speckit.esdlc.questions`, `/speckit.esdlc.gherkin`, `/speckit.tasks`, `/speckit.implement`, `/speckit.analyze`, `/speckit.checklist` |
| light | OpenCode `small_model` (titles, summaries) |

Red runs on flagship because it writes the frozen tests that green is judged against: the gates can prove a
test fails, not that it checks the right thing.

```powershell
ekit models setup          # lists the models in your project and global opencode.json, recommends one per tier
# or without prompts:
ekit models setup --flagship anthropic/<flagship-model> --standard ollama/qwen3:32b --light ollama/gemma4:31b-cloud
ekit models                # the routing table
git add .ekit/models.yaml .opencode opencode.json; git commit -m "chore: model tiers"
```

Then **restart OpenCode**. Every routed command starts with a line such as
`[ekit] tier: flagship · model: anthropic/<flagship-model>`; OpenCode also shows the active model in its UI.

- ekit writes `model:` into the frontmatter of each command in `.opencode\commands\` (OpenCode's per-command
  override) and of the kit's agents, and sets `small_model` in `opencode.json`. A Spec Kit upgrade regenerates
  the command files: run `ekit sync` afterwards (`ekit doctor` reports files where routing is missing).
- Red and green ledger entries record `model_tier` and `model_configured`. That is the configured model, not proof
  of the one that ran: switching models in the OpenCode UI is still possible.
- If the flagship model is unavailable, do not switch silently. Add a temporary override to `.ekit\models.yaml` and
  commit it:

  ```yaml
  overrides:
    speckit.esdlc.red: {tier: standard, reason: "flagship quota exhausted", approved_by: "Tech Lead", expires: 2026-12-15}
  ```

  Like policy overrides, an entry without `reason`, `approved_by` and an unexpired `expires` is ignored.
- `ekit doctor` warns when a tier's model has a smaller context window than recommended (flagship 64k,
  standard 32k), if `opencode.json` records it under `provider.<name>.models.<model>.limit.context`.
- `ekit models off` removes everything ekit wrote and deletes `.ekit\models.yaml`.
- Data-residency rules per tier (which models may see Restricted data) are reserved for the regulatory overlays
  (MVP2) and not enforced yet.

First live run to confirm: `ekit models` should list no command with "(no file under .opencode/)" for the
commands your Spec Kit version installs. If it does, Spec Kit writes its OpenCode commands somewhere else on your
version; report it so the kit can learn the location.

### K. Golden landing zone: changing the core and upgrading (0.3.0)

The golden core (`golden.yaml` `frozen:`: `src/app/main.py`, `src/app/core/**`, `src/app/api/**`,
`src/app/web/**`, base templates, `tests/conftest.py`, `tests/acceptance/conftest.py`,
`tests/acceptance/support/**`, the `000-*` scenarios and step modules, the conformance record, the Dockerfile)
is fingerprinted in `.ekit/golden.lock.yaml`. OpenCode refuses agent edits to it. Feature work never needs to
change it.

**A deliberate change to the core** (a person, reviewed like any other change):

```powershell
ekit baseline unfreeze --reason "ADR-0007: switch audit sink"    # audited in .ekit/freeze.yaml; restart OpenCode
# edit the core files (yourself, or have the agent do it in this window), keep its tests green
ekit adr new "Switch audit sink"                                 # if it changes a decision
ekit baseline accept --reason "ADR-0007 reviewed in PR 42"       # re-fingerprints and re-freezes; audited
ekit gate baseline; git add -A; git commit -m "chore(core): switch audit sink"
```

**Upgrading to a kit with a new golden revision:** `ekit upgrade` (section *B*) merges three ways. The base is
the golden revision you installed, "theirs" is the new revision, "ours" is your files.

| Your file | Result |
|---|---|
| unchanged since install | replaced by the new revision (`updated`) |
| changed, no overlap | both changes kept (`merged`) |
| changed, overlapping | `<<<<<<< project` / `>>>>>>> golden-new` markers left in the file (`conflicts`) |
| new in the new revision | added |
| deleted by you | left deleted (`kept`) |

With conflicts, `ekit gate baseline` fails (`BASE-GOLDEN-INTACT`). Resolve the markers yourself (not the agent),
run the tests, then `ekit baseline accept --reason "merged golden 1.1.0"` and commit. If the merge changed
`pyproject.toml`, run `uv lock` and `ekit run install` before the tests, and commit `uv.lock` with it.

**First golden project (pilot).** The golden application has not run outside the kit's static checks. On the
first project, run `ekit run install`, `ekit run unit`, `ekit run acceptance`, `ekit run typecheck` and
`ekit gate baseline`, and report anything that fails so the kit can ship it as golden revision 1.0.1.

```text
/speckit.constitution
/speckit.specify <feature description>
/speckit.clarify
/speckit.plan

```


`.ekit\` folder can stay; nothing reads it unless you run `ekit`.

## 5. Benchmarking: kit vs. no kit

The goal is to compare the two ways of working on the **same BRD**, under the **same
conditions**, and measure the outcomes that matter to an enterprise: correctness,
traceability, NFR coverage, rework and cost.

### 5.1 Set-up rules (fairness)

1. **Same input:** one real but small BRD, about 2–4 features.
2. **Same model and settings in OpenCode** for both arms, and the **same ekit CLI version** for every
   kit run (and for scoring Arm A in 5.4). Record it: a different CLI can judge the same artifacts differently.
3. **Same person driving**, or two people of similar experience, one per arm.
4. **Fresh repositories** for each run, created from the same starting commit.
5. **Hold-out acceptance tests.** Before either arm starts, someone who will not drive
   either arm writes an independent acceptance test pack from the BRD (black-box API/UI
   tests). Neither arm sees it. It is the referee.
6. **Repeat each arm at least 3 times.** LLM output varies between runs, so a single run
   proves nothing. Compare medians.
7. **Answer business questions identically.** Keep a "business oracle" sheet of answers the
   product manager has agreed. In the no-kit arm, answer only when the agent asks. In the
   kit arm, answer through the questions register. Record how many questions each arm raised.
8. **Same personal rules in both arms.** `$HOME\.config\opencode\AGENTS.md` applies to every session on the
   machine, so it affects both arms. Keep it identical (or empty) for the whole benchmark and record it.
9. **Waves off and one model in both arms** for the headline comparison: Arm A has no routing, so run Arm B
   without `ekit models setup` too. Measure waves and model tiers as separate experiments (Arm B with and
   without them), and record the routing table (`ekit models`) with each run.

### 5.2 Create the two arms

```powershell
# Arm A: no kit (repeat for run 1..3)
specify init bench-plain-r1 --integration opencode

# Arm B: with kit (repeat for run 1..3)
ekit init bench-ekit-r1 --stack fastapi-react --source bundled
```

Use the same stack in both. For Arm A, put the stack choice in the first
`/speckit.specify` prompt so the agent is not choosing a different stack.

### 5.3 Metrics and how to collect them

| # | Metric | How to measure | Better |
|---|---|---|---|
| M1 | **Functional correctness** | % of hold-out acceptance tests passing at "done" | higher |
| M2 | **Defects after done** | hold-out failures + bugs found in a 30-min exploratory test | lower |
| M3 | **Business questions surfaced** | count of distinct ambiguities raised *before* coding (Arm B: `open-questions.yaml`; Arm A: questions asked in chat) | higher (up to the real number) |
| M4 | **Wrong guesses** | business rules implemented differently from the oracle sheet without asking | lower |
| M5 | **NFR coverage** | score both repos against the NFR catalogue: run `ekit context --nfr all` and tick each NFR *Met / Partially / Not met* by reading the code (same reviewer for both) | higher |
| M6 | **Traceability** | % of acceptance criteria that can be traced to a test that checks them (see 5.4) | higher |
| M7 | **Test-first evidence** | Arm B: ledger entries; Arm A: `git log` shows tests committed before code? (yes/no per feature) | yes |
| M8 | **Lead time** | wall-clock from BRD received to all features "done" (note start/end times) | lower, but read together with M1–M6 |
| M9 | **Human interventions** | number of times you had to correct, redirect or re-prompt the agent | lower |
| M10 | **Rework** | lines changed after first "done" until the hold-out tests pass: `git diff --stat <done-commit> HEAD` | lower |
| M11 | **Cost** | tokens / spend per arm, from your model provider's usage dashboard (or OpenCode's usage stats, if your version shows them) | lower, but read together with M1–M6 |
| M12 | **Coverage & static checks** | run the same coverage, lint and dependency-audit commands in both repos | higher coverage, fewer findings |

Expect the kit to cost more in M8 and M11 (more steps, more tokens). The question the
benchmark answers is whether that buys enough in M1–M7, M9 and M10.

### 5.4 Scoring a no-kit repo with the kit's own gates (optional)

You can use the gates as a measuring tool on Arm A without changing Arm A itself. Work on
a **copy**:

```powershell
Copy-Item -Recurse C:\work\bench-plain-r1 C:\work\bench-plain-r1-scored
cd C:\work\bench-plain-r1-scored
ekit adopt --stack fastapi-react --source bundled --force --non-interactive
ekit gate all --format json --out reports\score.json
```

Arm A will lack most artifacts: no PRD, no `trace.yaml`, no `@SCN` tags, no conformance
tables. Gate failures there mostly measure **missing artifacts** rather than code quality.
Use this result to quantify the gaps for M5/M6, not as the headline score. M1 from the
hold-out tests is the headline.

### 5.5 Results sheet

Record one row per run in a spreadsheet (`benchmark.csv`):

```text
arm,run,brd,model,ekit_cli,kit_version,features,lead_time_min,interventions,questions_raised,wrong_guesses,holdout_pass_pct,defects_after_done,nfr_met_pct,ac_traced_pct,test_first(y/n),rework_lines,coverage_pct,lint_findings,sca_high,tokens,cost
plain,1,loan-v3,<model>,-,-,3,,,,,,,,,,,,,,,
ekit,1,loan-v3,<model>,0.3.0,0.3.0,3,,,,,,,,,,,,,,,
```

Compare the **median of each arm**. Report deltas for M1, M2, M4, M5, M6 and M10 first,
then cost and time.

### 5.6 Decision rule (suggested)

Adopt the kit as the default if, across 3+ runs, all of these hold:

- hold-out pass rate (M1) is equal or better;
- wrong guesses (M4) and defects after done (M2) are lower;
- NFR coverage (M5) and traceability (M6) are clearly higher;
- the extra lead time and cost stay within what you would spend fixing those gaps manually.

### 5.7 Arm C: golden vs. generated landing zone (0.3.0)

This measures whether the golden landing zone improves results on a low-strength model. Use the same BRD as
5.1 and the same standard-tier model in both groups (e.g. `ollama/gemma4:31b-cloud` or a qwen3), stack
`fastapi-jinja`, three runs each. **Assign the arm before the run. Never let the driver choose**, or the
comparison measures who picked what.

```powershell
ekit init bench-golden-r1 --stack fastapi-jinja --baseline golden --source bundled --non-interactive
ekit init bench-gen-r1    --stack fastapi-jinja --baseline generate --source bundled --non-interactive
```

Add these to the 5.3 metrics:

| # | Metric | How to measure | Better |
|---|---|---|---|
| M13 | Landing zone first pass | `ekit gate baseline` passes on the first attempt (y/n); tokens and minutes until it passes | yes / lower |
| M14 | Core drift attempts | edits to the core refused by OpenCode (session log), plus `ekit baseline drift` findings before each green (golden); for generate, count `SCN-000-*` regressions and baseline-module rewrites in `git log -p` | lower |
| M15 | Red quality | per feature: rejections by `RED-CLEAN-FAILURE`, `RED-STEPS-BOUND` and `RED-STATE-TYPED` before a clean red; `ekit fix-red` runs | lower |
| M16 | Smoke regressions | `SCN-000-*` failures seen in green runs | lower |

Keep golden as the default if M1 is equal or better, M13–M16 are better, and M8/M11 are no worse. Only then
build a golden landing zone for a second stack. Record `baseline_mode` and the golden version from
`.ekit/ledger/baseline.yaml` with each run.

## 6. Troubleshooting on Windows

| Symptom | Likely cause | Fix |
|---|---|---|
| `ekit` not recognized | uv tools folder not on PATH | `uv tool update-shell`, then open a new terminal |
| `Spec Kit CLI specify not found` | `specify` not on PATH for this shell | reinstall with `uv tool install specify-cli`, or set `$env:EKIT_SPECIFY = "C:\path\to\specify.exe"` |
| Slash commands missing in OpenCode | OpenCode started outside the project root, or not restarted after `ekit sync` | `cd` to the root and restart `opencode` |
| `Cannot tell which feature to check` | not on the `NNN-name` branch | `git switch 001-…`, or add `--feature 001-…` |
| `Cannot tell which PRD to check` | more than one PRD folder | add `--prd docs/requirements/<slug>` |
| `kit integrity` fails in `ekit doctor` | someone edited `.ekit\kit\` (often to add project guidance) | revert those files, or run `ekit upgrade`; put the guidance in the constitution IX+, `AGENTS.md` outside the ekit block, or your personal file (section *H*) |
| Your notes in `AGENTS.md` disappeared after `ekit sync` / `ekit upgrade` | they were written inside the `<!-- ekit:begin -->…<!-- ekit:end -->` block | restore them from git (`git log -p -- AGENTS.md`) and move them outside the block |
| The agent ignores your project notes or personal rules | OpenCode not restarted; started outside the project root; personal file not in OpenCode's global config folder | restart `opencode` from the project root; check the file is at `$HOME\.config\opencode\AGENTS.md` (or wherever your OpenCode build keeps global config) |
| A constitution diff touches principles I–VIII | `/speckit.constitution` reworded or "simplified" them | restore I–VIII from `.ekit\kit\preset\enterprise-baseline\templates\constitution-template.md`, keep only your IX+ changes; changing I–VIII needs an ADR and a new kit version |
| `spec`: "loan:AC-012 is planned for W2; the current wave is W1" (`SPEC-WAVE-SCOPE`) | the feature includes an AC from a later wave | drop it from this slice (`ekit wave scope FEAT-xx` shows what belongs now), or re-plan: edit the proposal, `ekit wave approve --by …` |
| `spec`: "… is not in the approved wave plan", or a gate note "the approved wave plan is no longer valid" | a new or changed BRD added ACs nobody has placed | place them in the proposal and approve again; approval lists the newly placed ACs |
| `plan`/`baseline`: "Deferred (W2) needs an approved wave plan" / "cannot be deferred" / "is required now" | `Deferred` used without waves, for a non-deferrable NFR, or after its wave became current | use Addressed, N/A or Waived with an ADR; or add the deferral to the proposal and approve (not possible for non-deferrable NFRs) |
| `ekit wave advance`: "… acceptance criteria of W1 have no green feature yet" | the wave is not finished | finish those slices, or `--carry` them to the next wave (recorded) |
| The agent says a command was denied (`ekit wave approve`, `ekit models`, `ekit unfreeze`, `ekit fix-red`, `ekit upgrade`) | these record a person's decision; `opencode.json` denies them to the agent's shell tool | run the command yourself in PowerShell |
| `ekit doctor`: "model routing … missing or outdated in …" | Spec Kit regenerated the command files (upgrade, `ekit sync` before 0.2.0) | `ekit sync`, then restart OpenCode |
| A routed command does not start with the `[ekit] tier: …` line | OpenCode not restarted after `ekit models setup` / `ekit sync`, or the model ignored the banner | restart OpenCode; check the active model in OpenCode's UI and `ekit models` |
| `ekit doctor`: "ekit CLI matches the project pin" fails | you run a different CLI version than the one in `.ekit/kit.lock.yaml` | install the pinned tag: `uv tool install --force git+https://…/sdd-kit.git@v<pinned>`; or, as a reviewed change for the whole team, `ekit upgrade` and commit `.ekit/` |
| Teammates or CI get a different gate result for the same commit | different ekit CLI versions (check logic differs), or `.ekit/` changes not committed | compare `ekit --version`; `git status .ekit`; see *What is pinned, and what is not* |
| Gate exits 2: "EKIT_REQUIRE_PINNED_CLI is set …" | CI runner installed another CLI than the pin | install the CLI tag named in the lock in the pipeline |
| "Kit … requires ekit >=0.3.0,<0.4 … (not >=0.3.0)" | your CLI is older or newer than the kit allows | install a CLI in the allowed range (`uv tool install --force git+…@v0.3.0`), or upgrade the project to a kit that allows your CLI |
| "kit.lock.yaml does not record an ekit CLI version" | project vendored by ekit < 0.1.4 | run `ekit upgrade` once with the team's CLI and commit `.ekit/` |
| `red`/`green`: `… Then "…" (scenario '…') has no step definition visible to tests/acceptance/…` (`RED-STEPS-BOUND`, `GREEN-STEPS-BOUND`) | a step has no definition the binding module can see: missing, defined under another keyword (`@given` for a `Then` step), or in a module that is not imported | at red: add or fix the definition and re-run `ekit gate red`. At green (the test is frozen): `ekit unfreeze <feature> --reason "…"`, stash the implementation, add the definition, `ekit gate red`, commit, restore the implementation |
| `red-recorded`/`green`: "… file(s) recorded at red are not committed as recorded" (`REDREC-COMMITTED`) | the commit after red was skipped or partial | commit the feature files, tests and `.ekit/ledger/` now; if a recorded file changed since red, restore it from the red run or go back to red |
| `baseline`/`plan`: "ADR number 0001 is used by 2 files" (`BASE-ADR-UNIQUE`) | a new ADR reused a number | rename all but one to the next free number the message names, and update `ADR-nnnn` references in conformance tables |
| `ekit status`: "Landing zone baseline: stale" | the conformance record, the pinned kit or (with waves) the active profiles changed since the last passing baseline | `ekit gate baseline`, then commit `.ekit/ledger/baseline.yaml` |
| `ekit status`: "Landing zone baseline: not run" on a project whose baseline passed earlier | the pass was before ekit 0.2.1, which started recording it | run `ekit gate baseline` once and commit the record |
| `red`: "failed with KeyError, not AssertionError" (or another exception name) (`RED-CLEAN-FAILURE`) | the scenario errored out of broken test glue (a dict key no step set, a typo'd fixture) rather than failing on a real assertion; pytest-bdd reports both as `failed`, so without this check it would freeze anyway | fix the test's step glue itself, not production code — `ekit unfreeze <feature> --reason "…"`, edit only the named test file, `ekit gate red` again until it fails cleanly on an assertion |
| OpenCode's edit tool refuses a `src/` file while a feature is unfrozen | since 0.2.2, `ekit unfreeze` also denies the feature's production source dir by default (see *3*) | that's intentional while you're fixing the test; re-freeze with `ekit gate red` to lift it, or re-run unfreeze with `--allow-src` if you really need both at once |
| `red`: "produced no report" | BDD runner not wired, or doesn't compile yet | run `ekit run acceptance` and read the error; the report path is in `ekit context` |
| `red`: "PASSES before implementation" | the test doesn't check the new behaviour | strengthen the assertion. Don't change the gate |
| `red`: "skipped — red needs the scenario to run and FAIL" | a `@skip`/`@wip` tag, a skip marker, or a tag filter in the runner config excludes the scenario | remove the skip or filter; a skipped scenario is not evidence that the test can fail |
| `green`: "never recorded failing (red) before green" after upgrading to 0.1.5 | the red ledger recorded `skipped`, not `failed` | `ekit unfreeze <feature> --reason "…"`, put the code back to stubs, `ekit gate red` |
| Gate note: "override for … ignored: `approved_by`, `expires` required" | override written for ekit < 0.1.5 | add the approver and an expiry date, or remove the override |
| `plan`/`baseline`: "Waived requires an ADR reference" although a date is given | since 0.1.5 a date is not an ADR reference | create the ADR in `docs/adr/` and cite `ADR-NNNN` |
| `ready`: "blocking question answered without `answered_by`" | the decision has no named owner | record who decided in `open-questions.yaml`, or re-import the CSV with `answered_by` filled |
| Maven wrapper errors | `JAVA_HOME` not set or not JDK 21 | set `JAVA_HOME`, then open a new terminal |
