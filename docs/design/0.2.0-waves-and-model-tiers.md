# ekit 0.2.0: waves and model tiers

Status: implemented in ekit 0.2.0 / kit 0.2.0. Follow-ups are listed at the end.

## 1. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Both features are **optional**. With no `.ekit/waves.yaml` and no `.ekit/models.yaml`, every gate behaves as in 0.1.5. | Adoption must not force a planning style or a model setup on anyone. |
| D2 | Waves are planned at **acceptance-criterion level**. A wave-slice of a PRD feature becomes its own Spec Kit feature folder (`specs/005-loan-application`, later `specs/011-loan-application-w2`); `trace.yaml` lists the AC subset. | "Show the face of the system first" needs thin slices of many features. Per-folder gates, frozen tests and the ledger keep working unchanged. |
| D3 | The **approved** plan lives in `.ekit/waves.yaml` and changes only through the CLI (`ekit wave approve / advance / decline`). Proposals live in `docs/planning/waves.proposed.yaml`, which agents and people may edit. | `.ekit/*` is already denied to the agent's edit tools; 0.2.0 also denies the approving CLI commands to the agent's shell tool. Approval records `approved_by`. |
| D4 | A later BRD for the **same product extends the same PRD** with continuing ids (BR-031, AC-045). A new PRD slug is for a separate initiative. Wave scope entries are qualified: `<slug>:AC-012`. | One AC namespace per product keeps the wave plan and traceability simple; qualification keeps several PRDs possible. |
| D5 | Models are routed by **tier** (`flagship`, `standard`, `light`), not by name. The kit owns command → tier; the project owns tier → model. **Red runs on flagship by default.** | Routing policy survives model changes and provider changes. Red writes the frozen contract that green is judged against, and the gates can prove a test fails but not that it checks the right thing. |
| D6 | ekit records the **configured** model, never claims the model that actually ran. | A developer can switch models in the OpenCode UI; the evidence says what it can prove. |

## 2. Waves

### Files

`docs/planning/waves.proposed.yaml` (editable, reviewed in PRs) and `.ekit/waves.yaml` (approved copy, CLI only):

```yaml
apiVersion: ekit/v1
kind: WavePlan
current: W1                       # set by the CLI, ignored in a proposal
waves:
  - id: W1
    goal: "Face of the system: shell, sign-in, one happy path per major feature"
    profiles: [backend, frontend] # optional; default: every profile of the stack
    scope: ["loan:AC-001", "loan:AC-004", "loan:FEAT-03"]   # FEAT-xx = all its ACs
  - id: W2
    scope: ["loan:AC-002", "loan:AC-003", "loan:AC-005"]
dependencies:                     # optional: prerequisite FEAT must start in the same or an earlier wave
  "loan:FEAT-03": ["loan:FEAT-01"]
defer:                            # NFRs not required until a later wave
  - { nfr: UX-01, until: W2, reason: "UI is a thin shell in W1", approved_by: "Head of Product" }
```

### Validation (`ekit wave validate`, also run by `approve` and `advance`)

- wave ids unique; `current` names a wave;
- every scope entry names a PRD that exists and an AC/FEAT it defines;
- **every AC of every PRD is in exactly one wave** (a new BRD's ACs therefore have to be placed before the plan validates again);
- every wave has at least one AC;
- dependencies: the prerequisite feature has an AC in the same or an earlier wave than the dependent's first AC;
- deferrals: the NFR exists, is not on the kit's **non-deferrable list** (`policy/waves.policy.yaml`), and `until` is a later wave than the first one; `reason` and `approved_by` are present.

### Commands

| Command | Who | Effect |
|---|---|---|
| `ekit wave status [--brief]` | anyone | current wave, per wave: AC count, specified / green, deferrals due; `--brief` prints `waves: undecided | off | on (W1)` |
| `ekit wave init` | person | writes a proposal skeleton: all ACs of all PRDs in W1, an empty W2 |
| `ekit wave decline` | person | records `waves: off` in `.ekit/project.yaml` so the agent stops asking |
| `ekit wave validate [--proposal]` | anyone | runs the checks above |
| `ekit wave approve --by NAME` | person | validates the proposal and writes `.ekit/waves.yaml`; keeps `current`; records history and any **re-deferral** (an `until` moved later) |
| `ekit wave advance --by NAME [--carry]` | person | moves `current` to the next wave. Refused while an AC of the current wave has no green feature, unless `--carry` moves those ACs to the next wave (recorded). |
| `ekit wave scope FEAT-xx [--prd]` | agent | prints which ACs of that feature are in the current wave and which come later |

`approve`, `advance`, `decline` and `ekit models …` are denied to the agent through `permission.bash` rules in `opencode.json`, managed like the existing edit rules. `ekit unfreeze` and `ekit upgrade` join that list.

### Gate behaviour (waves on)

| Where | Behaviour |
|---|---|
| `spec` gate, new check `SPEC-WAVE-SCOPE` (`wave.scope`) | every AC in `trace.yaml` must be in the current or an earlier wave; an AC planned for a later wave is an error naming that wave |
| `nfr.conformance` (plan and baseline) | new status `Deferred (W2)`: accepted only for an NFR the approved plan defers until that wave, while the current wave is earlier; once that wave is current it is an error. Non-deferrable NFRs are always an error. |
| profile checks (`profile.command`, `profile.required_paths`, `profile.environment`, `bdd.run`, `bdd.vacuous_steps`) | only profiles active in the current wave run; each gate report carries a note naming the inactive profiles. NFRs that apply only to an inactive role are not required yet and become required when the role becomes active. |
| everything else | unchanged |

With waves off, `SPEC-WAVE-SCOPE` passes silently (an info line with `-v`), `Deferred` is rejected with "needs an approved wave plan", and all profiles are active.

## 3. Model tiers

### Files

Kit (pinned): `policy/models.policy.yaml`

```yaml
tiers: [flagship, standard, light]
commands:                 # OpenCode command name -> tier
  speckit.esdlc.brd: flagship
  speckit.constitution: flagship
  speckit.esdlc.baseline: flagship
  speckit.plan: flagship
  speckit.esdlc.red: flagship
  speckit.specify: standard
  ...
agents: { requirements-analyst: flagship, test-author: flagship }
small_model: light
min_context: { flagship: 64000, standard: 32000 }
```

Project (committed, CLI only): `.ekit/models.yaml`

```yaml
apiVersion: ekit/v1
kind: ModelRouting
tiers:
  flagship: { model: "anthropic/claude-opus-x" }
  standard: { model: "ollama/qwen3:32b" }
  light:    { model: "ollama/gemma4:31b-cloud" }
overrides:                # temporary, e.g. flagship unavailable
  speckit.esdlc.red: { tier: standard, reason: "...", approved_by: "...", expires: 2026-12-31 }
```

### Behaviour

- `ekit models setup` lists the models configured in OpenCode (project and global `opencode.json`), recommends one per tier, and writes `.ekit/models.yaml`; `--flagship/--standard/--light` for non-interactive use. `ekit models show`, `ekit models off`.
- On `ekit models setup` and every `ekit sync`, ekit writes `model:` into the frontmatter of each routed command in `.opencode/commands/` (and `.opencode/command/`, for older layouts) and each kit agent, plus a short banner the agent prints first: `[ekit] tier: flagship · model: <id>`. `small_model` is written into `opencode.json`. Everything ekit writes is marked and removed again by `ekit models off`.
- Overrides follow the policy-override rules: `reason`, `approved_by` and an unexpired `expires`, otherwise ignored and reported.
- Red and green ledger entries record `model_tier` and `model_configured`. `ekit status` shows the routing table; `ekit doctor` reports commands whose `model:` line is missing (typically after a Spec Kit upgrade: run `ekit sync`) and models whose known context window is below the tier minimum.
- Reserved, not enforced: a per-tier `allowed_data` list for data-residency rules (regulatory overlays, MVP2).
