# ekit 0.2.3: `ekit fix-red`

Status: implemented in ekit 0.2.3 / kit 0.2.3.

## 1. What this fixes

0.2.2 shipped `RED-CLEAN-FAILURE` and the narrow unfreeze, but fixing a frozen test's own glue by
hand still meant the person doing it had to get the git plumbing right themselves every time:

1. Unfreeze.
2. Get the feature's production source back to how it looked the last time this scenario was
   genuinely red — so the test fix is proven against the same failure, not against code the test
   was never red against.
3. Run `ekit gate red`.
4. Put the production source back, review the test diff, commit.

On the same real project that found 0.2.2's gaps, step 2 was done with `git stash` the first time
— which worked only because the implementation hadn't been committed yet. The second time, a
`.patch` file had already been applied (outside OpenCode's edit tool, so the narrow-unfreeze deny
rules never saw it) and the implementation was already committed; `git stash` had nothing to grab,
and the person had to work out by hand which files to revert and how to put them back. That's
mechanical, repetitive, and exactly the kind of step where a slip (reverting the wrong commit,
forgetting to restore a file) costs real time to notice and undo.

## 2. `ekit fix-red`

`ekit fix-red <feature> --reason "..."` ( `src/ekit/fixred.py`, wired in `cli.py` as `cmd_fix_red`):

1. Requires the feature to already be frozen (same precondition as `ekit unfreeze`) and every
   active profile's production source dir (`layout.source`, reused from 0.2.2's narrow-unfreeze —
   `freeze.source_dirs()` / `freeze.source_patterns()` are now shared between the two features) to
   be clean per `git status --porcelain`. A dirty tree is refused outright rather than guessed at:
   restoring exactly afterwards depends on there being nothing uncommitted to lose.
2. Reads the feature's ledger (`.ekit/ledger/<feature>.yaml`) for the `git_head` recorded on its
   last `red` entry. No red entry, or one with no recorded `git_head` (written by an ekit older
   than the one that started recording it), is refused with a message pointing at the manual path.
3. Unfreezes narrowly, same as `ekit unfreeze` does by default since 0.2.2.
4. Checks the production source dirs back to their state at that red commit — `git checkout
   <red_commit> -- <dirs>`, not `git stash`, because by the time this command is reached for, the
   implementation is usually already committed and there is nothing to stash. A file that exists
   now but didn't exist at the red commit (created by this feature's own implementation) can't be
   removed by a checkout of a tree that never had it, so it's moved to a temp dir instead and moved
   back afterward, rather than deleted.
5. Runs `ekit gate red` for the feature and captures its report.
6. Restores the production source to exactly what it was before, in a `finally` — whether red came
   back clean or not, and whether the gate run itself raised.

It returns `(clean, report)`; the CLI prints the gate's own report text and, on a clean result,
the exact next commands (review the diff, `git add -A && git commit -m "test(...): red (...)"`,
then `ekit gate green`) rather than running them — **it never commits anything**. A clean
`ekit gate red` here is evidence a human still reviews, same as every other step in this pipeline.

**Two directory-existence edge cases**, both found while building this rather than from a report,
same mechanism as `RED-CLEAN-FAILURE`'s own motivation (mechanical checks cannot skip past inputs
most people rarely hit):

- Checking out a directory from a commit it never existed in as a tracked tree (e.g. one created
  entirely by this feature's own implementation) makes `git checkout <rev> -- <dir>` fail on a
  pathspec match error — filtered out before the revert step (`revertible`, via `git ls-tree -r
  --name-only <rev> -- <dir>`).
- The exact same failure mode applies on the way *back*: a stack profile whose `layout.source` is
  an empty directory with nothing committed in it (e.g. `frontend/jinja`'s `src/app/web` on a
  backend-only feature) has no tracked entry at `HEAD` either, so the unconditional restore
  checkout failed in exactly the same way the revert-to-red checkout did. The same filter
  (`restorable`) is applied to the restore call too — this was caught by `tests/test_ekit_023.py`
  exercising a real two-profile (`fastapi-jinja`) project, not reasoned out in advance.

## 3. Why it's denied to the agent's shell tool

Same reasoning as `ekit unfreeze`, `ekit upgrade` and the wave-approval commands: this is a
person's call about their own test, made once they've decided the test's glue (not the
implementation) is wrong. Giving an agent the ability to invoke it on its own would hand back
exactly the judgment call narrow-unfreeze exists to take out of the agent's hands in 0.2.2 — it
would just be reached by a different command. `freeze.ALWAYS_BASH` now lists `"ekit fix-red*"`
alongside `ekit unfreeze*`, and `AGENTS.block.md`'s "never run" list says the same thing in words.

## 4. Not in 0.2.3

| Item | Why deferred |
|---|---|
| Auto-committing a clean result | Would remove the one review step every other red/green transition in this pipeline still requires of a human; the toil this command removes is git plumbing, not the decision to commit. |
| Recovering when the ledger's `red` entry predates `git_head` being recorded | Rare (only affects features red before `ekit` started recording it); the error message points at the pre-0.2.3 manual path, which still works. |
| Detecting *why* red isn't clean (still broken glue vs. a genuinely different bug) | Out of scope — `ekit gate red`'s own report (including 0.2.2's `RED-CLEAN-FAILURE`) already says this; `fix-red` only automates getting back to a state where that report is meaningful. |
