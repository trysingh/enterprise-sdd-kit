# ekit 0.5.0: change requests from the prompt (brownfield change lane)

Status: **implemented** in ekit 0.5.0 / kit 0.5.0 (golden `fastapi-jinja` 1.0.1, unchanged).
Covered by unit and CLI tests (`tests/test_ekit_050_change.py`; 203 tests in total pass). **Not yet
run against a live Spec Kit + OpenCode install.**

## 1. Why

Up to 0.4.1, work entered the pipeline in one of two ways:

- `/speckit.esdlc.brd <file>`: a BRD becomes a PRD (`FEAT-`, `AC-`), questions, then one Spec Kit
  feature per `FEAT-`. This suits a new product or a large release.
- `/speckit.specify <free text>`: possible, but the wrapper warned that it "will not be traceable"
  and asked for a BRD first.

Brownfield work is mostly neither. It is a sentence typed by a developer or copied from a ticket:
*"after I open a chat the unread badge still shows 3"*, *"add a 'mark all as read' button"*. Writing
a BRD file for that and passing its path is friction nobody accepts, so the request either went
through `specify` untraced or bypassed the kit. Two further gaps blocked brownfield use even when a
user tried:

1. **A bug fix's red proves nothing when it is stubbed.** The red step (and `RED-ROUTE-STUBBED` in golden
   projects) assumes new behaviour behind new `not_implemented()` stubs. For a bug the code exists. A model
   following the red command replaces the buggy function with a 501 stub, red passes, and the "test came
   first" evidence no longer says anything about the bug.
2. **A behaviour change to a delivered feature could never go green.** The old feature's scenarios are
   frozen and assert the old behaviour. The new scenario asserts the new behaviour. Green runs the whole suite,
   so one of them always fails. The only way out was `ekit unfreeze` on the old feature, which leaves
   that feature's `GREEN-TESTS-UNCHANGED` failing for good, because its red can never be recorded again
   (its other scenarios now pass).

## 2. What 0.5.0 adds

### 2.1 The change request

`/speckit.esdlc.change <request text>` takes the request as typed. The agent:

1. classifies it: `bug` (observed differs from expected), `enhancement` (changes an existing feature),
   `feature` (new capability);
2. runs `ekit change candidates "<text>"`, a deterministic word-overlap ranking of existing feature
   folders, and reads only the top one or two (cheap for smaller models);
3. runs `ekit change new --type … --title … --affects … --text "<request>"`, which allocates `CR-NNNN`,
   creates `docs/requirements/cr-NNNN-<slug>/` and keeps the request **verbatim** in `request.md`
   (`--file -` reads stdin; or the agent pastes it in when the text has quotes or line breaks);
4. fills `change.yaml` (bug: `observed`, `expected`, `reproduction`; `supersedes:` the existing scenarios
   the change makes wrong), and writes a small `brd.md` / `prd.md` (normally one `FEAT-01`) /
   `open-questions.yaml`;
5. runs `ekit gate intake --prd CR-NNNN`, then hands off to `/speckit.specify CR-NNNN`.

The CR folder **is** a PRD folder. Nothing downstream needed a new code path: `trace.yaml` points
`prd:` at it, and the spec, scenarios, plan, red and green gates run unchanged. `--prd CR-0007` resolves
anywhere a PRD folder is accepted (`ekit gate intake|ready`, `ekit questions …`).

`ekit change new` is open to the agent (it records, it decides nothing). `ekit change list` and
`ekit status` show every CR with its phase (intake / spec / red / green) and the spec folder(s) that
implement it.

### 2.2 The TDD cycle per change type

Same cycle, same gates: spec → Gherkin → plan → tasks → **red** → commit → **implement** → **green**.
What red has to prove differs:

| Type | Red | Production code at red | Green |
|---|---|---|---|
| `bug` | the new scenario **reproduces** the defect: fails on an assertion that shows the observed behaviour | **untouched and committed**: no stubs, no partial fix | the fix; every other scenario still passes |
| `enhancement` | new scenarios fail (501 stubs for new routes) | stubs only; golden: in the **affected** feature's package | changed behaviour; superseded scenarios retired (2.3) |
| `feature` | as any feature | stubs only, own package | as any feature |

`RED-BUG-REPRODUCED` (`change.bug_reproduced`) enforces the bug row: it fails red if any file under the
profile's production source directories differs from HEAD, or if a scenario's failing step reports a
501 or `NotImplementedError`. This is stronger evidence than ordinary red: the failing test ran against
the exact code that is in production.

### 2.3 Superseding a delivered scenario

When a change makes an existing frozen scenario wrong, the CR lists it under `supersedes:`. Before
green, **a person**:

1. removes that scenario from the delivered feature's `.feature` file (in an editor: the agent's edit
   tool is still denied);
2. runs `ekit change retire <feature> <SCN-…> --by CR-NNNN --reason "…"`.

`retire` verifies that only the named scenarios were removed (the Feature header, Background and every
other scenario are byte-identical to the committed, fingerprinted version), and that the CR lists them.
It then appends a `rebase` entry to that feature's ledger (who, when, CR, reason, retired ids, new
fingerprints, the contract copied from red) and re-applies the freeze. `GREEN-TESTS-UNCHANGED`,
`REDREC-COMMITTED` and `ekit freeze` read the latest `red` **or** `rebase` entry, so the delivered
feature stays green-able. `ekit change retire*` is in the agent's bash deny list.

`GREEN-CHANGE-SUPERSEDED` fails the CR's green while a superseded scenario still exists;
`RED-CHANGE-SUPERSEDES` reports the same as a warning at red, so the person can retire it early.

### 2.4 Golden projects

`ekit feature package <feature>` prints the package(s) a feature's code lives in. For a `bug` or
`enhancement` that affects existing features, those are the **affected** features' packages (e.g.
`f003_chat`), not a new `f008_cr0007_…` package. `ekit fix-red` reverts the same packages.

## 3. New and changed checks

| Gate | Check | Type | Applies to |
|---|---|---|---|
| intake | `INTAKE-CHANGE-VALID` | `change.valid` | CR folders: id matches folder, valid type and title, request kept verbatim, affected features exist, superseded ids exist (or are already retired), bug has `observed` and `expected` (or `[TBD: OQ-…]`); warns when a bug or enhancement names nothing it affects, and when the PRD has more than one `FEAT-` |
| ready | `READY-CHANGE` | `change.valid` (`ready: true`) | as above, plus no `[TBD` left in the bug facts |
| red | `RED-BUG-REPRODUCED` | `change.bug_reproduced` | bug CRs |
| red | `RED-CHANGE-SUPERSEDES` (warn) | `change.supersedes_retired` | CRs with `supersedes:` |
| green | `GREEN-CHANGE-SUPERSEDED` | `change.supersedes_retired` | CRs with `supersedes:` |

All are no-ops for ordinary PRDs and features, so existing projects see no change in their gate results.

## 4. Files

```
docs/requirements/cr-0007-unread-badge-does-not-clear/
  request.md            # verbatim request; never edited after intake
  change.yaml           # id, type, title, ticket, recorded_by/at, affects, supersedes, bug facts
  brd.md  prd.md  open-questions.yaml   # small; same templates and gates as a BRD intake
specs/008-cr0007-unread-badge/          # Spec Kit feature; trace.yaml: prd: docs/requirements/cr-0007-…, change: CR-0007
```

## 5. Limits

- **Refactors, chores and dependency bumps** (no observable behaviour change) have no honest red: nothing
  can fail before the change. They stay outside the change lane; the green gate run on the affected
  features (`ekit gate green --feature …`, suite exit 0) is the regression check for them. A later
  version could add a `refactor` type that requires a passing characterisation run instead of a red one.
- **Waves on**: a CR is a PRD folder, so its ACs must be placed in a wave and approved like any new BRD's
  before `/speckit.specify` accepts them (`SPEC-WAVE-SCOPE`). This is deliberate (scope stays governed)
  but adds a person step for every CR; projects that use waves may want a standing "current wave takes
  CRs" practice.
- `RED-BUG-REPRODUCED` judges the profile's production source directories. Code outside them (a SQL view,
  a config file) is not covered; review those diffs.
- `ekit change candidates` is word overlap, not understanding. It narrows reading; the agent still decides.
- Non-pytest-bdd stacks: the 501 check reads the Cucumber JSON error message, which Cucumber-JVM and
  cucumber-js also write; it has only been exercised with pytest-bdd's format.
