# ekit 0.2.2: a clean red, and a narrower unfreeze

Status: implemented in ekit 0.2.2 / kit 0.2.2.

## 1. What this fixes

Debugging a real feature (conversation persistence) on a 0.2.0 project surfaced two gaps, both
found the expensive way — mid-implementation, not at red:

| # | Gap | Root cause |
|---|---|---|
| 1 | `ekit gate red` froze a scenario whose `And` step read `scenario_state["separate_conversation_ids"]`, a key no step in that scenario ever set. It ran clean during implementation... as a `KeyError`, not the intended behavioural gap. | pytest-bdd reports a `KeyError` from a step and a real `AssertionError` from a step identically, as `failed`. `RED-RUN` only checks that a scenario *is* `failed`; it never asked *why*. |
| 2 | The same feature also had a scenario whose `When` step ("opens the **empty** conversation with") had no step definition at all — hidden behind gap #1, because the scenario errored at an earlier step and pytest-bdd never reached the undefined one. | This specific shape (an undefined step hidden behind an earlier failure) is exactly what 0.2.1's `RED-STEPS-BOUND` was built to catch statically — but this project was still on kit 0.2.0, so it wasn't there yet. Confirms 0.2.1 was the right fix for *that* class of bug; it does not help with #1. |
| 3 | Told to fix gap #1 by unfreezing, editing the test, and re-running red, an agent instead spent that turn on unrelated implementation work (models, session handling, API wiring) and committed it under a "fix step glue" message — without touching the test file at all. | A broad instruction ("find the step and fix it") left room to wander once the deny-rule on the test file was lifted; nothing stopped it from also touching `src/`. |

Only #3 is really about agent care. #1 and #2 are gate gaps — a general-enough instruction can't
close them, because the agent genuinely can't see what's missing until the report in front of it
says so, and the report was allowed to say "red passed" when it hadn't.

## 2. RED-CLEAN-FAILURE

A scenario recorded as red must fail on an assertion about missing behaviour (or, for non-pytest
styles, a 404/501 — already stated in `/speckit.esdlc.red`'s step 5), never error out of the test
itself. Implementation:

- `gherkin.read_cucumber_elements()` returns the raw cucumber-JSON element per scenario id (not
  just the aggregated status string `read_cucumber_reports()` already gave every other check).
- `gherkin.failure_exception(element)` takes the last `SomeError:`/`SomeException:`-shaped name
  out of the failed step's `error_message` — the innermost, most specific exception in whatever
  traceback pytest-bdd wrote there.
- `bdd.clean_failure` (gate id `RED-CLEAN-FAILURE`, in the `red` gate, right after `RED-RUN`) reads
  the same report `RED-RUN` just wrote, and for every scenario this feature expects red, rejects
  it if the exception name isn't on the allow-list (default: `AssertionError` only).

This is deliberately a narrow, late check — it inspects the one real run just performed, rather
than trying to guess a scenario's behaviour statically. It complements `RED-STEPS-BOUND` (0.2.1)
rather than replacing it: that one catches an undefined step *nothing ever reaches*; this one
catches a step that *did* run and threw something other than the assertion it was supposed to.

**False positives.** A team whose house style deliberately raises something other than
`AssertionError` for "not implemented yet" (a `NotImplementedError` stub, say) can add it to the
check's `allow:` list in policy, or use the standard reason/approver/expiry override for a one-off.
We expect this to be rare: in the project that found this gap, every genuine red failure was in
fact an `AssertionError` (HTTP-client-style tests naturally produce one), and both actual bugs were
something else.

## 3. Narrow unfreeze

`ekit unfreeze <feature> --reason "..."` now also denies edits to the feature's production source
directory (each active profile's `layout.source`, e.g. `src/app/**`) for as long as the feature
stays unfrozen — on top of lifting the test-file deny, not instead of it. `ekit gate red` clears
the source-deny the moment it re-freezes. `--allow-src` skips this for the rare case where staying
unfrozen on both sides at once is actually wanted.

This isn't a judgment that the agent can't be trusted with production code in general — it already
has full access to it during `/speckit.implement`. It's that *this specific window* has one job
(fix the test), and the permission system can enforce that boundary mechanically instead of
depending on how precisely each unfreeze instruction happens to be worded.

Command text (`/speckit.esdlc.red`) and the `AGENTS.md` block both say the same thing in words, for
agents and situations the mechanical rule doesn't cover (a profile with no declared `layout.source`,
a stack ekit doesn't model yet): edit only the named test file in that turn; two step functions
covering near-identical scenarios are not interchangeable — the one with fewer Given steps must set
up what it needs itself, not assume a sibling scenario's setup ran first.

## 4. Not in 0.2.2

| Item | Why deferred |
|---|---|
| Distinguishing a *legitimate* non-`AssertionError` red failure automatically (rather than via an allow-list) | Would need per-framework convention beyond what cucumber-JSON's `error_message` reliably gives; the allow-list is simple and the override path covers the rest. |
| Narrowing the source-deny below the whole `layout.source` tree (e.g. only files the feature's own tasks name) | `tasks.md` task-to-file mapping isn't structured enough to parse reliably yet; whole-tree deny is coarse but unambiguous. |
| Applying `RED-CLEAN-FAILURE`-style reasoning to `GREEN-RUN` | Green expects `passed`, not `failed` — there's no equivalent "wrong exception" shape to check there. |
