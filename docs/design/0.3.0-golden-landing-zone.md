# ekit 0.3.0: golden landing zone, and structural fixes for the 0.2.1–0.2.5 bug classes

Status: implemented in ekit 0.3.0 / kit 0.3.0, golden landing zone `fastapi-jinja` 1.0.0.
Covered by unit and CLI tests (`tests/test_ekit_030.py`). Not yet run against a live Spec Kit +
OpenCode install, and the golden application's own test suite has not been run (see section 8).

## 1. Why

Every release from 0.2.1 to 0.2.5 fixed a gap found on the same real project (an intranet
messenger, `fastapi-jinja`, Windows, smaller models). Each fix either **detected** the problem in a
gate after the agent had produced it, or **reworded** a command so the agent would be less likely to
produce it. Both help, but on a low-strength model, detection means a loop of failed gates and
rewording means hoping the model reads carefully.

0.3.0 changes what the model starts from and what it is allowed to decide:

- The landing zone is no longer generated. For `fastapi-jinja`, the kit ships a **golden landing
  zone**: a reviewed codebase that already meets every platform-scope NFR. It is installed
  deterministically by `ekit init`.
- The parts of that codebase the 0.2.x bugs lived in are **frozen**: core modules, the shared test
  helpers and the smoke scenarios. Feature work happens in defined **seams**.
- Decisions the command texts used to leave to the model are made by the CLI: which feature is
  active, which ADR number is next, and the constitution's filled-in fields.

The pipeline, the gates and the evidence model are unchanged. Projects that choose
`--baseline generate`, and every other stack, behave as in 0.2.5.

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | The golden landing zone is part of the vendored kit (`kit/golden/<stack>/`), hashed in `kit.lock.yaml` like every other rule. | One source of truth and one pinning mechanism. A team that forks the kit forks its golden code too. |
| D2 | It is **opt-out, not opt-in**: `ekit init --stack fastapi-jinja` installs it unless `--baseline generate` is passed. Brownfield folders always get `generate`. | The point is to help low-strength models, which is the default case. Golden code does not fit a repository that already has code. |
| D3 | The golden revision (`golden.yaml` `metadata.version`, e.g. `1.0.0`) is versioned **separately** from the kit and keyed on the kit tree, **not on the constitution version**. | Principles I–VIII change only with a new kit version, so the kit pin already covers them. Project principles IX+ do not map deterministically to code. |
| D4 | The installed copy is fingerprinted per file in `.ekit/golden.lock.yaml`. This is the merge base for upgrades and the reference for drift. | Without a recorded base, a three-way merge and "has the core changed?" are both guesswork. |
| D5 | A new golden revision arrives through `ekit upgrade` as a **three-way merge** (`git merge-file`). Conflicts are left with markers and block the baseline gate. | Weak models should not resolve merge conflicts in security, error-handling or logging code. A person resolves them and runs `ekit baseline accept`. |
| D6 | Core files are denied to the agent's edit tools. Changing them is a person's two-step act: `ekit baseline unfreeze --reason` then `ekit baseline accept --reason`. Both are audited and both are denied to the agent's shell. | This is the 0.2.2 narrow-unfreeze principle applied to the landing zone. "Extend, never rewrite" becomes a mechanical rule. |
| D7 | Constitution ratification is deterministic (`ekit constitution ratify`), and principles I–VIII are checked word for word (`BASE-CONSTITUTION`). | Before 0.3.0 a flagship-tier model filled four placeholders, and only pull-request review protected I–VIII. |

## 3. Bug class → structural fix

| Found in | What happened | 0.2.x remedy (kept) | 0.3.0 structural fix |
|---|---|---|---|
| 0.2.1 | A `Then` step had no definition. It was hidden because the scenario failed earlier (a 501 stub), so red froze a test that could never pass. | `RED-STEPS-BOUND` static scan | A **shared step library** in the frozen `tests/acceptance/conftest.py` covers HTTP requests, status, headers, JSON fields, problem documents, page text and CSRF form posts. A feature writes only its domain-language steps, so there are far fewer steps to forget. Patterns are `parsers.re` with `[^"]+`, so none shadows another (a test checks this). |
| 0.2.1 | Two ADRs were numbered `0001`. | `BASE-ADR-UNIQUE` / `PLAN-ADR-UNIQUE` | `ekit adr new "Title"` allocates the next free number. Commands and the agent rules say to use it, and golden ships `0001` and `0002`. |
| 0.2.2 | A step read `scenario_state["…"]`, a key no step of *that* scenario set. pytest-bdd reported the `KeyError` like an assertion failure, so red froze broken glue. | `RED-CLEAN-FAILURE` | A **typed `ScenarioContext`** (`ctx` fixture, one per scenario). `ctx.recall(key)` raises `MissingScenarioStateError` naming what the scenario *does* have. `RED-STATE-TYPED` rejects dict state fixtures and `scenario_state[...]` in golden projects. `RED-CLEAN-FAILURE` gives this error its own message. |
| 0.2.2 | While unfrozen to fix a test, the agent implemented unrelated production code instead. | narrow unfreeze denies `layout.source` | The core cannot be edited at any time (D6). Feature code has one home, its **feature package**. |
| 0.2.2/0.2.3 | `GREEN-TESTS-UNCHANGED` fingerprints only feature files and bound test modules, not `conftest.py` or shared helpers. A test could be "fixed" by editing a helper. | review | Helpers, `conftest.py` and the `000-*` scenarios are golden core: denied to edits, and `GREEN-GOLDEN-INTACT` fails on any change. |
| 0.2.4 | `fix-red` reverted the feature's **whole** source directory to its last-red commit. On a multi-feature project that also stripped shared code added since, and the failure message could only explain this. | improved message | Golden projects keep each feature's code in `src/app/features/f<NNN>_<slug>/` (`ekit feature package`). `fix-red` reverts only that package. Shared code lives in the core or the registry and is never reverted. |
| 0.2.5 | With empty `$ARGUMENTS`, the agent took the example name in a command (`001-user-admin`) as the feature to implement. | reworded command text | **No example names remain** in any command (a test checks this). The commands run `ekit feature current --for red\|implement "$ARGUMENTS"`, which prints exactly one real folder or fails with the list of real ones. It never returns `000-*`. |
| 0.2.5, anticipated | The golden reference slice is itself an example a model could mistake for, or wire into, a real feature. | — | `RED-NO-EXEMPLAR` / `GREEN-NO-EXEMPLAR` reject a feature that *is* `000-reference-slice`, imports `f000_reference`, binds its feature file or reuses `SCN-000-*`. The slice is never mounted in production. |
| pre-0.3.0 | Principles I–VIII were protected only by pull-request review. | review | `BASE-CONSTITUTION` (D7). |

One gap was found while building this release, of the same kind as the 0.2.2 and 0.2.3 edge cases.
`gherkin.failure_exception` recognises only exception names ending in `Error` or `Exception`. A
first draft named the new exception `MissingScenarioState`, which the reader would have returned as
`None`, and `RED-CLEAN-FAILURE` would then have *accepted* the broken glue. It is
`MissingScenarioStateError`, and a test pins that the reader sees it.

## 4. The golden landing zone (`fastapi-jinja` 1.0.0)

`src/ekit/kit/golden/fastapi-jinja/`:

| Path | Role |
|---|---|
| `golden.yaml` | Manifest: version, `render` (files with `__PROJECT_NAME__` / `__PROJECT_SLUG__`), `rename` (`dot_gitignore` → `.gitignore`, so packaging tools never treat kit content as their own config), `frozen`, `seams`, `exemplar`, `post_install` (`uv lock`), and `agent_rules` injected into `AGENTS.md` |
| `tree/src/app/core/` | settings (CFG-01, fails fast, refuses dev auth in prod), structlog + redaction (OBS-01), RFC 9457 errors and `not_implemented()` (API-02), middleware for correlation id, security headers, CORS and CSRF cookie (OBS-02, SEC-06, SEC-08), OIDC `current_user` + `require()` (SEC-01/02), SQLAlchemy engine (DATA-01), shared httpx client with timeouts (REL-01), `t()` i18n (UX-02) |
| `tree/src/app/api/`, `web/`, `main.py` | `/api/v1` prefix, health live/ready, Jinja templates with CSRF-checked `web_router()`, app factory with lifespan (REL-03), optional OpenTelemetry (OBS-04) |
| `tree/src/app/features/registry.py` | **Seam**: the one place feature routers are registered |
| `tree/src/app/features/f000_reference/` | Reference slice: API, page, form POST, schemas, service, the feature's own settings |
| `tree/tests/acceptance/conftest.py`, `support/` | Shared steps, `ScenarioContext`, `feature_file()` path helper |
| `tree/specs/000-landing-zone/`, `000-reference-slice/` | Smoke `SCN-000-01..03`, reference `SCN-000-11..16` |
| `tree/docs/engineering/baseline-conformance.md` | All 22 platform-scope NFRs that apply to the stack, each `Addressed` with evidence |
| `tree/docs/adr/0001`, `0002` | ADR process; why the project starts from golden |
| `tree/` (other) | `pyproject.toml` (deps, ruff, mypy strict, pytest), `.python-version`, `Dockerfile` (multi-stage, non-root), Alembic, `.gitignore`, `.dockerignore`, gitleaks pre-commit |

Seams (`ekit baseline status` prints them): the feature package, the registry,
`src/app/templates/features/<slug>/`, `migrations/versions/`, `tests/unit/features/` and
`tests/acceptance/test_<NNN>_<slug>.py`. A feature's own settings use its own `BaseSettings` class
and env prefix, so `core/settings.py` never needs editing for a feature.

`uv.lock` is **not** shipped. It is resolved on the user's machine by `post_install` (`uv lock`,
which needs network access once). Until then, `BASE-SKELETON` names the exact command to run.

## 5. Install, freeze, accept, upgrade

```text
ekit init demo --stack fastapi-jinja [--baseline golden|generate] [--name "Demo Bank"]
  specify init … ; vendor kit ; extension + preset ; seed constitution
  golden.install            copy tree (render, rename), refuse on clashes, .gitignore line-merged
                            write .ekit/golden.lock.yaml {version, tree_sha256, frozen, files: sha256}
                            post_install: uv lock (skipped with EKIT_SKIP_POST_INSTALL=1)
  constitution.ratify       name, version 1.0.0, dates, stack section; IX placeholders removed
  freeze.freeze_baseline    permission.edit deny for every frozen pattern (state key `baseline`)
  AGENTS.md                 golden agent_rules inserted ahead of the profile rules
```

- `ekit baseline status | drift` — anyone. Drift kinds: `changed`, `deleted`, `added` (a new file
  inside the core) and `conflict` (markers left by an upgrade).
- `ekit baseline unfreeze --reason` / `accept --reason` / `install` — a person only (denied to the
  agent's shell). `accept` refuses while conflict markers remain. It re-fingerprints, records
  history and re-freezes, and makes the baseline record stale (`golden_lock_sha256` is part of its
  fingerprint), so `ekit gate baseline` must pass again.
- `ekit baseline install` puts golden into a project created by `ekit init` before 0.3.0, if
  nothing in it clashes.
- `ekit upgrade`, golden projects: the current golden directory is snapshotted before the new kit is
  vendored. For each file:
  - project unchanged from the old golden → take the new revision (`updated`);
  - project changed → `git merge-file` (`merged`, or `conflicts` with markers);
  - new in golden → added;
  - deleted by the project → left deleted (`kept`);
  - removed from golden → left in place and reported (`removed`).
  The lock moves to the new version and the core is re-frozen with the new patterns.

## 6. Checks added

| Gate | Check id | Type | Golden only? |
|---|---|---|---|
| baseline | `BASE-CONSTITUTION` | `constitution.intact`: I–VIII differ → error; unratified or missing → warn | no |
| baseline | `BASE-GOLDEN-INTACT` | `golden.intact`: drift or conflict markers → error | yes (info otherwise) |
| red | `RED-STATE-TYPED` | `bdd.typed_state`: dict state fixture or `scenario_state[...]` in a bound module | yes |
| red | `RED-NO-EXEMPLAR` | `golden.no_exemplar` | yes |
| green | `GREEN-GOLDEN-INTACT` | `golden.intact` | yes |
| green | `GREEN-NO-EXEMPLAR` | `golden.no_exemplar` | yes |

`RED-CLEAN-FAILURE` gains a specific message for `MissingScenarioStateError`. `BASE-SKELETON` names
the command for a missing `uv.lock`. The ledger's `baseline.yaml` records `baseline_mode` and the
golden stack and version. `ekit status` and `ekit doctor` show them, and doctor adds rows for the
constitution and the golden core.

New CLI: `ekit constitution ratify|check`, `ekit baseline …`, `ekit feature current|package`,
`ekit adr new`, and `ekit init|adopt --baseline --name`.

## 7. Measuring it: benchmark arm C

The runbooks' section 5 gains arm C. The same BRD and the same standard-tier model (e.g.
`gemma4:31b-cloud` or a qwen3) run under `--baseline golden` and `--baseline generate`, three runs
each. **The arm is assigned, not chosen by the driver**, to avoid selection bias. Additional metrics:

| # | Metric | How |
|---|---|---|
| M13 | Landing-zone first pass | `ekit gate baseline` passes on the first try (y/n), plus tokens and minutes until it passes |
| M14 | Core drift attempts | edits to the core refused by OpenCode (count in the session log) + `ekit baseline drift` findings at each green |
| M15 | Red quality | per feature: `RED-CLEAN-FAILURE`, `RED-STEPS-BOUND` and `RED-STATE-TYPED` rejections before a clean red; `ekit fix-red` runs |
| M16 | Smoke regressions | `SCN-000-*` failures seen in green runs |

Decision rule: keep golden as the default if M1 (hold-out pass rate) is equal or better, M13–M16 are
better, and lead time and cost are no worse. Only then build a golden tree for a second stack.

## 8. Known limits

- **Not yet executed:** the golden application and its test suite have not been run. The kit's
  build environment had no FastAPI or pytest-bdd and no network. The tree passes `ruff check` and
  `ruff format --check` under its own configuration, and the kit's tests check statically that it
  parses, that every Gherkin step in it is bound, that no step pattern shadows another, and that
  its conformance record satisfies `BASE-CONFORMANCE`. **First thing to do on a real machine:**
  `ekit init … --stack fastapi-jinja`, `ekit run install`, `ekit run unit`, `ekit run acceptance`,
  `ekit run typecheck`, `ekit gate baseline`. Report anything that fails as a golden 1.0.1 fix.
- `GREEN-TESTS-UNCHANGED` still does not fingerprint helpers in **generated** projects; only golden
  projects get that coverage (through `GREEN-GOLDEN-INTACT`).
- OpenCode edit rules cover the edit tools, not shell commands. `GREEN-GOLDEN-INTACT` is the
  backstop, as `GREEN-TESTS-UNCHANGED` is for tests.
- `fix-red` package scoping assumes the red step created the feature package (with
  `not_implemented()` stubs), which `/speckit.esdlc.red` now says to do. If the package was created
  only during implementation, its files are moved aside for the red run, as in 0.2.3.
- The flagship tier still routes `/speckit.esdlc.baseline` and `/speckit.constitution`. In golden
  projects both are now verification or IX+ only; moving them to the standard tier is a policy
  change left to measurement.
