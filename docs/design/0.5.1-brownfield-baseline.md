# ekit 0.5.1: brownfield baseline (assess, don't impose)

Status: **implemented** in ekit 0.5.1 / kit 0.5.1 (golden `fastapi-jinja` 1.0.1, unchanged).
Covered by `tests/test_ekit_051_brownfield.py`; 227 tests in total pass. **Not yet run against a live
Spec Kit + OpenCode install.**

## 1. Why

On an existing repository `ekit gate baseline` could not pass honestly, although the baseline command
says brownfield means "assess, don't impose":

1. `BASE-SKELETON` treated the greenfield file list of the profile as hard errors.
2. The conformance table allowed only `Addressed`, `N/A`, `Waived`. A real gap fitted none, so the agent
   wrote `Waived` without an ADR (it cannot approve waivers) and the gate failed on the missing ADR.
3. "not a git repository" gave no cause. A common one is git's "dubious ownership" check, which needs a
   different fix than `git init`.

## 2. What changed

- `Project.is_brownfield`: true when `.ekit/project.yaml` has `mode: brownfield` (written by `ekit init`
  when code exists); greenfield when absent.
- Conformance status `Gap` (in `baseline/nfr-catalog.yaml`): applies, not met yet. Needs a justification
  and a remediation reference: ticket (`ABC-123`), task (`T012`), `#45` or an ADR id. NFR ids (`SEC-01`),
  scenario, PRD and gate-check ids (`SCN-003-01`, `FEAT-01`, `AC-03`, `BASE-ENV`) are not accepted as tickets;
  a change request id (`CR-0007`) is. Brownfield: warning
  `<NFR> gap: <justification> (remediation <ref>)`. Greenfield: error.
- `Waived` is unchanged: a person's decision, ADR reference required. Ticket references belong to `Gap`.
- `profile.required_paths`: warnings in brownfield with a hint to add the file or record a Gap/Waived.
- `git_state(root)` in `project.py`: `ok`, `no-git`, `dubious`, `not-repo`. The two git warnings
  (`profile.environment`, `ledger.red_committed`) name the cause and the fix.
- Prompts and templates: gaps get `Gap`; additive files (pin file, acceptance conftest, Dockerfile) are
  added rather than gapped; the agent never invents a waiver. Constitution principles I–VIII are unchanged (a test pins them).

## 3. Checks

| Check | Greenfield | Brownfield |
|---|---|---|
| `BASE-SKELETON` missing path | error | warn (+ hint) |
| `BASE-CONFORMANCE` `Gap` with a remediation ref | error | warn |
| `Gap` without a remediation ref | error | error |
| `Gap` without justification | error | error |
| `Waived` without ADR | error | error |
| `profile.environment` missing pin file | error (hint: one-line file, e.g. `"3.12"`) | same |
| Git unusable | warn with cause and fix | same |

## 4. Limits

- `Gap` is accepted in any conformance table of a brownfield project, including feature plans; the
  prompts only direct it to the baseline record.
- A warning is not an approval: a `Gap` stays visible on every run of the gate until remediated.
- The remediation reference is checked for form only, not looked up in a ticket system.
- `git_state` runs one `git rev-parse` per check; it does not repair ownership or init a repository.
- Projects that predate the `mode` key are treated as greenfield: add `mode: brownfield` to
  `.ekit/project.yaml` by hand if the repository was adopted.
- The kit now requires `ekit >=0.5.1,<0.6`: an older CLI would accept `Gap` without enforcing its rules.
