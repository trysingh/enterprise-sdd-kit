# ekit 0.7.0 — happy path first: design stage, Day-0 seams, rigor by wave

Status: **design, decisions taken (section 10)**, ready to implement. Builds on waves (0.2.0), golden landing zone
(0.3.0), change lane (0.5.0) and forward baseline (0.5.1 / 0.6.0). Worked example of the design artifact:
`claude/messenger-architecture-v0.md`.

## 1. Why

0.1.x → 0.6.4 were found on one small app, and almost every release added a check plus more command text. The app
never converged. Three causes, none of which another check fixes:

1. **No design stage.** The pipeline goes requirement → spec → scenario → red → code per feature. Nothing fixes the
   system's shape (topology, seams, core data, interface) before the first test is frozen, so red step code guesses at
   objects and methods that do not exist yet, and every wrong guess costs an unfreeze / fix-red cycle.
2. **Full rigor from line one.** Freeze, ledger, step scans and NFR tables apply before there is anything stable to
   protect. Tokens go to ceremony around code that is about to change.
3. **No gate asks "can a user actually use the features we planned?"** Every stage can be green while the product
   never works as a whole.

Enterprise teams get a thin but working version against *simulated* cross-cutting concerns (a fixed set of dev
users), then layer real identity, logging, audit, tracing and security on top once the face of the app appears.
0.7.0 makes that the kit's default.

## 2. Principles

- **P1 Happy path first — but a real one.** The first delivery covers **every key feature identified at planning**,
  working together as a POC-grade app: real persistence, several users, state that changes and is seen by others,
  variation in data. "Happy" means no error/edge handling yet — not one trivial rule per scenario.
- **P2 Day 0 = seams, not controls.** Cross-cutting concerns exist from the first line as interfaces with dummy
  implementations. Real controls replace dummies later. Business logic never changes when they do.
- **P3 Design before spec.** A short, approved architecture note fixes topology, ports, core data, interface and
  slices. Everything after it is written in the language of those ports and operations.
- **P4 Rigor is a property of the wave.** Policy says which checks run at which wave. Red-first, freeze and ledger
  start once the seams are stable.
- **P5 Done is proven by traceability, not sign-off.** Each requirement is traced to a feature, to the operations
  and pages a user can call, and to a journey run that called them successfully.

### 3.1 `happy-path.md` (added to intake)

Per `FEAT-`: the capability, who uses it, what they do, what they (and others) then see. Plus the **cross-feature
journeys** — sequences that span several features the way real use does (e.g. user A creates something, user B
finds it, acts on it, A sees the result). Plus the cross-cutting concerns the BRD implies. Written by the intake
model. Gate `intake`: file exists; every `FEAT-` marked key appears in ≥1 journey.

### 3.2 The design artifact (new)

`architecture.md` — fixed sections, ≈1–2 pages: topology (with the option rejected), ports, core data model,
interface, Day-0 seams, slices, decisions. `design.yaml` — the same facts, machine-readable, and the **spine of
traceability**:

```yaml
topology: central-server
ports:
  - {name: MessageStore, methods: [append, history], dependency: get_message_store}
seams:
  principal:  {impl: dev-users, file: config/dev-users.yaml}
  audit:      {impl: log}
  request_id: {impl: middleware}
  config:     {impl: env}
  data_owner: {field: owner_id}
features:                                    # requirement -> feature -> what a user can call
  FEAT-01:
    brs: [BR-001, BR-002]
    operations: [send_message, list_messages]   # FastAPI operation_id = OpenAPI operationId
    pages: ["GET /chat/{peer}"]
slices:
  - id: S0
    features: [FEAT-01, FEAT-02, FEAT-03]
    journeys: [J-01, J-02]                     # from happy-path.md
decisions:
  - {id: D1, title: Topology, status: accepted, adr: ADR-0002}
```

Gate **`design`** (`DESIGN-*`): sections present; every key `FEAT-` has ≥1 operation or page and is in exactly one
slice; every BR of an in-scope feature is listed; every port has a dependency and ≥1 method; decisions have a
status and accepted ones cite an ADR; all five seams declared. `ekit design approve --by` is a person command
(bash-denied to the agent). Model tier: **flagship**.

### 3.3 W0 lane: `/speckit.esdlc.slice <S-id>`

Builds one slice against `design.yaml`, in feature packages of the golden core. No spec/plan/tasks documents, no
freeze, no ledger. Required:

- each port as a `Protocol` + one adapter + one in-memory fake; unit tests on services using the fakes;
- every operation in `design.yaml` exists with that `operation_id`;
- **journeys** (below) for each journey of the slice.

**Journeys (decision for Q3): Gherkin, through the HTTP API, with generic steps.** Gherkin keeps one readable style
across all waves and lets the business review what "done" means. To avoid the custom glue code that caused most
0.2.x–0.6.x defects, the golden core ships a **generic API step library**, so most journeys need no new step code:

```gherkin
@J-01 @FEAT-01 @FEAT-02
Feature: Two colleagues exchange messages and a file
  Scenario Outline: <sender> writes to <receiver> and shares a file
    Given I am signed in as "<sender>"
    When I call "send_message" with peer "<receiver>" and body "<text>"
    Then the call succeeds
    And I remember "id" from the response as "msg"
    Given I am signed in as "<receiver>"
    When I call "list_unread"
    Then the response contains "<sender>" with count 1
    When I call "list_messages" with peer "<sender>"
    Then the response contains the remembered "msg"
    And the call to "list_unread" now shows "<sender>" with count 0
    Examples:
      | sender | receiver | text            |
      | asha   | ravi     | hello           |
      | ravi   | meera    | report attached |
```

Steps address operations **by `operation_id`** (resolved from the app's OpenAPI), switch principal by dev-user
name, chain state with `remember` / `the remembered`, and vary data with outlines — multi-user, stateful,
cross-feature. Feature-specific steps are allowed for pages or assertions the generic library can't express.
Journeys run against the real app (`TestClient`, real SQLite in a temp dir). Model tier: **standard**.

### 3.4 Traceability instead of sign-off (decision for Q4)

During the journey run, a test-only middleware records every call: `operation_id`, principal, status, journey tag.
Output: `reports/journeys.json`. Gate **`smoke`** then checks, deterministically:

| Check | Fails when |
|---|---|
| `SMOKE-JOURNEYS-PASS` | any journey of the slice fails |
| `SMOKE-OPERATION-EXISTS` | an operation in `design.yaml` is not in the app's OpenAPI |
| `SMOKE-OPERATION-EXERCISED` | a key feature's operation was never called successfully (2xx) by any journey |
| `SMOKE-PAGE-REACHABLE` | a declared page doesn't return 200 for a signed-in dev user |
| `SMOKE-FEATURE-COVERED` | a key `FEAT-` has no journey tagged with it |
| `DESIGN-PORTS-IMPLEMENTED` | a port of the slice is missing or lacks a declared method |
| `BASE-SEAMS-PRESENT` | the core doesn't expose the five seams |

`ekit trace matrix [--format md|csv|json]` prints **BR → FEAT → operation/page → journey → last result**, the
single artifact a reviewer reads. `ekit trace postman` exports a Postman collection built from OpenAPI plus the
journeys (with a dev-user auth preset), so anyone can call each feature by hand — the proof is automated, the
manual check is available, nobody has to sign.

## 4. Day-0 seams in the golden core (`fastapi-jinja` golden 1.1.0)

| Seam | Golden core ships | Replaced later by |
|---|---|---|
| Principal | `get_principal()` → `Principal(id, display, roles)`. **`DevUserProvider`** (decision Q2): fixed users and passwords in `config/dev-users.yaml`; HTTP Basic for the API (works in Postman), a minimal sign-in form + session cookie for pages | OIDC/SSO provider |
| Audit | `AuditSink.record(actor, action, target, data)`; `LogAuditSink` | durable / tamper-evident store |
| Request id | middleware: `X-Request-Id` in or generated, on every log line | OpenTelemetry trace context |
| Config | settings from env (`APP_ENV`) | vault / platform config |
| Data owner | each feature table has an owner or participant column | row-level authz policies |

`config/dev-users.yaml` example:

```yaml
# DEV ONLY. Refused at startup when APP_ENV is not dev|test. Passwords are deliberately fake.
users:
  asha:  {password: asha-dev,  display: Asha,  roles: [user]}
  ravi:  {password: ravi-dev,  display: Ravi,  roles: [user]}
  admin: {password: admin-dev, display: Admin, roles: [admin]}
```

The app refuses to start with `DevUserProvider` unless `APP_ENV` is `dev` or `test`. `ekit`'s secret checks
allow-list this one file by path and the `-dev` convention. Journeys sign in as these names. ≈60 lines in the frozen
core. Logging format, tracing exporters, security headers, rate limits, SAST/SCA are **not** Day 0.

`GREEN-NO-DUMMY` (enterprise rigor): fails while `DevUserProvider` or `LogAuditSink` is wired for a non-dev
environment; override with reason/approver/expiry as usual.

## 5. Rigor by wave (`policy/rigor.policy.yaml`)

```yaml
levels:
  skeleton:   # W0
    on:  [intake, ready, design, smoke, BASE-SEAMS-PRESENT, BASE-GOLDEN-INTACT, ENV-01, lint, unit]
    off: [spec, scenarios, plan, red, red-recorded, green, NFR-feature-rows, coverage, sca]
  standard:   # W1..: everything as in 0.6.4
    on: all
  enterprise: # overlay waves
    on: all
    add: [GREEN-NO-DUMMY, overlays]
```

`waves.yaml` gains `rigor:` per wave (W0 `skeleton`, W1+ `standard`). Every gate report names the level and lists
checks skipped because of it. Raising rigor is a person action (`wave advance`); lowering it is an override.
After adoption, W0 journeys stay in the suite as regression tests and are fingerprinted at the adoption point like
red evidence, so later work can't quietly break the happy path.

## 6. Defaults and migration

- `ekit init` (greenfield, golden): **happy-path lane on by default** (decision Q1). `--lane classic` keeps 0.6.4.
- Existing projects: unchanged (no `rigor:` → `standard`). `ekit design init --from-code` drafts a design artifact
  from existing packages and OpenAPI for a person to complete; `ekit trace matrix` works once it exists.
- Brownfield `adopt`: starts at `standard`; design artifact recommended.

## 7. Token effects (expected, to be measured)

- W0 skips ~5 model passes per feature (spec, Gherkin, plan, tasks, red) and every freeze/unfreeze cycle.
- Generic API steps remove most hand-written step glue — the dominant defect class so far.
- After adoption, red tests target declared ports and operations: nothing to guess.
- Flagship tier concentrates on intake, design and red; W0 build and implement run on standard.
- 0.7.x follow-ups from the lean review: `ekit scaffold red`, `ekit next`, failures-only gate output,
  `ekit context --for <stage>`, token counts per command in the action log.

## 8. Risks and limits

- **W0 code without red-first** can be weaker; mitigated by fakes-based unit tests, journeys, golden core, and
  red-first for everything after adoption.
- **Skeleton becomes permanent.** W1 work can't be specified until the adoption point passes; `GREEN-NO-DUMMY`
  keeps dummies visible.
- **Exercised ≠ correct.** `SMOKE-OPERATION-EXERCISED` proves a feature was called successfully, not that every
  assertion is meaningful. Journeys' `Then` steps carry that; `RED-STEPS-ASSERT`-style vacuous-step scanning also
  runs on journey step modules.
- **UI-only features** (no API) are covered by `SMOKE-PAGE-REACHABLE` only — reachability, not behaviour. Browser
  automation is out of scope for 0.7.0.
- Non-golden stacks get design, rigor levels and the trace matrix; Day-0 seams and the generic step library come
  with their golden cores.

## 10. Decisions

| # | Question | Decision |
|---|---|---|
| Q1 | Happy-path lane default for greenfield golden | **On** |
| Q2 | Dummy identity | **Fixed dictionary of dev users and passwords** (`config/dev-users.yaml`), dev/test only |
| Q3 | W0 test style | **Gherkin journeys over the HTTP API with a generic step library**: multi-user, stateful, cross-feature, data-varied; must cover every key feature |
| Q4 | Manual smoke sign-off | **Not needed.** Replaced by automated traceability BR → FEAT → operation/page → journey → result (`smoke` gate, `ekit trace matrix`), plus a generated Postman collection for hand checks |

## 11. As implemented (differences from the note)

- `rigor.policy.yaml` quotes its `on` / `off` keys (unquoted they are booleans in YAML 1.1); the loader accepts both.
  A name matches a gate id, a check id or an alias; a check's own id or alias in `on` beats its gate in `off` (so
  `lint` and `unit` still run inside the otherwise-off `green` gate). `add` checks run only at the level that lists
  them; with no rigor configured they are left out of the report entirely (identical to 0.6.4).
- `design` and `smoke` carry `lane: happy-path` in the gate policy: `ekit gate <id>` always works, `ekit gate all`
  runs them only in that lane. `SMOKE-RUN` runs the profile `journeys` command (set `EKIT_SMOKE_NO_RUN=1` to judge
  reports already on disk) and `SMOKE-W0-INTACT` implements "fingerprinted at the adoption point".
- Journeys are recorded with a route template as well as an `operation_id`, so `SMOKE-PAGE-REACHABLE` reads pages
  from the same file. `GREEN-NO-DUMMY` looks at `design.yaml` seams and at non-dev environment files
  (`.env.*`, `deploy/`, `config/` …) for `APP_PRINCIPAL_PROVIDER=dev-users` / `APP_AUDIT_SINK=log`.
- Leaving W0 is a different path in `ekit wave advance`: the per-AC "green feature" test is replaced by the adoption
  conditions (design approved and unchanged, `smoke` passing, baseline recorded). Journeys are fingerprinted in
  `.ekit/ledger/w0-journeys.yaml`.
