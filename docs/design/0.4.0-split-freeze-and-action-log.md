# ekit 0.4.0: split freeze (contract vs glue) and the action log

Status: **implemented** in ekit 0.4.0 / kit 0.4.0 (golden `fastapi-jinja` 1.0.0, unchanged).
Covered by unit and CLI tests (`tests/test_ekit_040_split.py`, `test_ekit_040_red.py`,
`test_ekit_040_log.py`; 188 tests in total pass). **Not yet run against a live Spec Kit + OpenCode
install** (see §8). Section 10 lists where the implementation differs from the first draft of this
note.

## 1. Why

### 1.1 What goes wrong today

After `ekit gate red` passes, `freeze_feature` denies the agent's edit tools on two things:

- the feature's `.feature` files (`specs/<feature>/features/*`);
- every **bound test module**, by exact path. A module counts as bound if it mentions the feature
  file or `SCN-<NNN>-` (`checks.py:_feature_bound_tests`).

`GREEN-TESTS-UNCHANGED` then requires both to be byte-identical to the last red fingerprint.

On the messenger project, the step functions in bound test modules repeatedly turned out to be
**logically wrong** but still passed red. Examples:

- a step calls a method the client or `ScenarioContext` does not have;
- a step uses the wrong object (the response instead of its JSON);
- a `Given` returns, or stores, a value of the wrong shape for later steps.

Red does not catch these. The **first** failing step (a 501 from a `not_implemented()` stub)
ends the scenario, so the broken later steps are never executed. This is the same masking that
0.2.1 (`RED-STEPS-BOUND`) and 0.2.2 (`RED-CLEAN-FAILURE`) addressed. Those checks cover
*unbound* steps and *errors at the failing step*, but not *logic errors in steps that never ran*.

In green the implementation removes the 501, the hidden step finally runs and crashes, and the
agent cannot fix it: the module is frozen. The agent stalls, often with no clear message, until a
person runs `ekit unfreeze --reason`. On a weak model this repeats per feature, sometimes per
scenario.

### 1.2 What the freeze is actually protecting

The governance claim is: *the behaviour the system must show was fixed before the code existed,
and the implementer could not weaken it.* That claim lives in:

- the **Gherkin**: scenarios, steps, examples and the literal expected values in them;
- the **binding**: which step text maps to which keyword and pattern, and which scenarios are
  bound;
- the **assertions** in `Then` steps: what is checked and against which expected values.

It does **not** live in the plumbing that turns a step into an HTTP call. Examples of plumbing
are which client method is used, how a response is parsed, and what a `Given` hands to the next
step. Freezing the plumbing protects nothing and blocks the agent.

### 1.3 No history to debug from

When the agent stalls, there is no record of what it did. The only records today are YAML
`history` lists inside state files (`freeze.yaml`, `waves.yaml`, `golden.lock.yaml`) and the
per-feature ledgers. Nothing records gate runs that failed, CLI commands, or the agent's own
tool calls (edits refused by the deny rules, shell commands, retries).

## 2. Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Split the frozen test surface into **contract** (hard-frozen) and **glue** (agent-editable, guarded by gates). | Keeps the governance claim and removes the main cause of unfreezes (§1.2). |
| D2 | Prove a glue change did not weaken the test **by running it**: amended glue must still fail cleanly against the feature's code as it was at red (`GREEN-GLUE-STILL-RED`). | Static rules can be gamed or missed. Running against the red-time code is the same evidence red gave, regenerated. It reuses the `fix-red` checkout machinery. |
| D3 | Catch glue logic errors **before** the freeze: type-check the bound test modules at red (`RED-GLUE-TYPED`). | Wrong methods, wrong objects and wrong return shapes are type errors. Golden projects already run `mypy --strict`, and `ScenarioContext` is typed. |
| D4 | In golden projects, red failures must be **501 from `not_implemented()`**, not 404, unless the scenario asserts a 404 (`RED-ROUTE-STUBBED`). | A 404 at red means the test calls a route the stubs never defined, which usually means a wrong URL in the glue. Today `RED-CLEAN-FAILURE` accepts it. |
| D5 | Give the agent a sanctioned way to stop: `ekit blocked <feature> --reason` writes a record and prints what a person must do. | Turns "agent silently stalls" into a logged, actionable request. |
| D6 | Add an append-only, hash-chained **action log** at `.ekit/logs/actions.jsonl`. It covers every `ekit` command and every agent tool call (through an OpenCode plugin). | Debugging and audit (§1.3). The hash chain makes tampering through the shell detectable, since OpenCode edit rules do not cover shell commands. |
| D7 | `freeze.mode: split \| strict` in `.ekit/project.yaml`. Golden projects default to `split`, generated projects to `strict`. | Teams that want the 0.3.0 behaviour keep it. `split` depends on D2 and D3, which are strongest with the golden tree. |

## 3. Split freeze

### 3.1 What is frozen and what is guarded

| Surface | `strict` (0.3.0) | `split` (0.4.0) |
|---|---|---|
| `specs/<feature>/features/*.feature` | edit-denied, byte fingerprint | **edit-denied, byte fingerprint** (unchanged) |
| Bound test module: step decorators (keyword, pattern, `target_fixture`), `scenario()` / `scenarios()` calls | edit-denied | **editable, contract-fingerprinted**: any change fails `GREEN-CONTRACT-INTACT` |
| Bound test module: `Then` assertion summary (see §3.2) | edit-denied | **editable, checked**: may not weaken (`GREEN-GLUE-NOT-WEAKENED`) |
| Bound test module: everything else (`Given` / `When` bodies, helpers, imports, parsing) | edit-denied | **editable**, re-proved by `GREEN-GLUE-STILL-RED` and recorded in the ledger |
| Golden core: `conftest.py`, `support/`, `000-*` | edit-denied (`GREEN-GOLDEN-INTACT`) | unchanged |
| New `conftest.py` or helper module under `tests/acceptance/` in a generated project | not covered | `GREEN-NO-SHADOW-GLUE`: error |

In `split` mode, `freeze_feature` stops adding bound modules to `permission.edit`. The `.feature`
pattern and the `ALWAYS` rules stay.

### 3.2 The contract fingerprint

At red, `flush_pending_records` adds `contract` to the ledger entry next to `fingerprints`. For each
bound module, the contract is computed from the AST:

```yaml
contract:
  tests/acceptance/test_003_send_message.py:
    bindings_sha256: …        # sorted (keyword, pattern, parser kind, target_fixture) + scenario() calls
    then_steps:
      "the response status is {code:d}":   {asserts: 1, literals_sha256: …}
      "the message appears in the thread": {asserts: 2, literals_sha256: …}
```

`literals_sha256` hashes the literal constants inside each `assert` expression and inside calls to
the shared-library assertion helpers. Changing `201` to `200` in a `Then` body changes the contract.

### 3.3 Checks for glue changes (green gate, `split` mode)

| Id | Type | Fails when |
|---|---|---|
| `GREEN-CONTRACT-INTACT` | `ledger.contract_intact` | bindings changed, a bound scenario is no longer bound, or a `.feature` file changed |
| `GREEN-GLUE-NOT-WEAKENED` | `bdd.glue_not_weakened` | a `Then` step has fewer asserts or different assertion literals; or the module gains any of: `pytest.skip`, `xfail` or `skip` markers, a `return` before the first assert in a `Then` step, a `try` / `except` wrapping an assert, `assert True`, `assert x == x`, `or True` in an assert |
| `GREEN-GLUE-STILL-RED` | `bdd.replay_red` | only runs if the glue changed since red. It checks out the feature package (golden) or source dirs (generated) at the last red `git_head`, runs the feature's scenarios with the **current** glue, and requires every one to fail cleanly (the `RED-RUN` and `RED-CLEAN-FAILURE` rules). It then restores the tree in a `finally` block, the same as `fixred.py`. |
| `GREEN-NO-SHADOW-GLUE` | `bdd.no_shadow_glue` | a new `conftest.py` or step-definition module appears under `tests/` that the red fingerprint did not have and that defines a step pattern the feature uses |

`GREEN-TESTS-UNCHANGED` stays in `strict` mode. In `split` mode it is replaced by the four checks
above.

When the glue changed and all four pass, the green ledger entry records:

```yaml
glue_amendments:
  - file: tests/acceptance/test_003_send_message.py
    red_sha256: …
    green_sha256: …
    diff: .ekit/evidence/003-send-message/glue-1.diff   # committed with the green commit
    functions: [given_a_peer_is_online, when_i_post_message]
    replay_red: passed
```

The pull-request reviewer sees exactly which glue changed and that it was re-proved red.

### 3.4 Catching glue errors before the freeze (red gate)

| Id | Type | Scope | Fails when |
|---|---|---|---|
| `RED-GLUE-TYPED` | `bdd.glue_typecheck` | golden (and any stack whose profile defines `run.typecheck`) | `mypy` (project config) reports errors in the bound test modules. This is what catches wrong methods, wrong objects and wrong return shapes in steps that red never executes. |
| `RED-ROUTE-STUBBED` | `bdd.route_stubbed` | golden | a scenario fails with 404 although none of its `Then` steps asserts 404. Message: the route is missing from the feature package's stubs, or the glue calls the wrong URL. |

Both run before `RED-RUN`, so a weak model gets the error while the module can still be edited.

### 3.5 When the agent is genuinely stuck: `ekit blocked`

`ekit blocked <feature> --reason "..." [--file path] [--scenario SCN-…]`:

- is **allowed** to the agent's shell (it is not in `ALWAYS_BASH`);
- appends `{phase: blocked, at, reason, file, scenario, model_configured, git_head}` to the
  feature's ledger and to the action log;
- prints what the person should run. That is `ekit unfreeze <feature> --reason …` if the
  `.feature` itself is wrong. In `split` mode, glue errors should not need a person.

`ekit status` shows open blocked records per feature. A later red or green entry closes them.

The agent rules in `AGENTS.md` and the `implement` command text say: *If a frozen `.feature` file
or a contract check stops you, run `ekit blocked` with the reason and stop. Do not work around it.
You may fix step bodies in the feature's own test module. The green gate will re-prove them red
and record the diff.*

## 4. Action log

### 4.1 Location and format

- `.ekit/logs/actions.jsonl`: one JSON object per line, UTF-8, LF. It is covered by the existing
  `ALWAYS` edit deny on `.ekit/*`.
- The file rotates at 5 MB to `actions-<UTC timestamp>.jsonl`. The chain continues across files
  (§4.4).
- `.gitignore` gets `.ekit/logs/` by default. Set `log.commit: true` in `.ekit/project.yaml` for
  teams that want the log in the repository. The ledger stays the system of record for gate
  evidence either way.

### 4.2 What is logged

**A. Every `ekit` command.** A wrapper in `cli.main` sits between `parse_args` and `args.fn`. It
writes one `cmd.start` and one `cmd.end` event per run, sharing a `run_id`.

```json
{"v":1,"seq":412,"ts":"2026-11-06T04:12:09.531Z","run_id":"8f…","kind":"cmd.end",
 "cmd":"gate","args":["red","003-send-message"],"feature":"003-send-message",
 "actor":"rachpal@…","via":"agent","session":"ses_…",
 "exit":1,"duration_ms":18234,"ekit":"0.4.0","kit":"0.4.0","git_head":"a1b2c3d","dirty":true,
 "gate":{"name":"red","result":"fail",
         "checks":{"RED-GLUE-TYPED":"error","RED-RUN":"skipped"},
         "findings":["tests/acceptance/test_003_send_message.py:41 \"ScenarioContext\" has no attribute \"get\""]},
 "prev":"sha256:…"}
```

- `via` is `agent` when `EKIT_ACTOR=agent` is set (the plugin in B sets it for shell tool calls),
  otherwise `person`. `session` comes from the plugin when present.
- Findings are capped at 20 per event, 500 characters each.
- Events from state-changing commands carry their own fields. Examples: `freeze` and `unfreeze`
  (`paths`, `reason`), `blocked`, `fix-red`, `baseline accept`, `wave approve` and `upgrade`
  (merge results). The existing YAML `history` lists keep being written, so nothing that reads
  them changes.

**B. Every agent tool call.** A kit-shipped OpenCode plugin, `kit/opencode/plugin/ekit-audit.js`,
is installed to `.opencode/plugin/`, which the `ALWAYS` deny on `.opencode/*` protects. It uses the
plugin `tool.execute.before` / `after` hooks to write:

- `tool.call` events: tool name; file path for edit and write tools; command for the shell tool
  (truncated to 500 characters); outcome (`ok` / `error` / `denied`); duration; session; model and
  agent when OpenCode exposes them.
- Edit **content is not logged**, only path and before/after sha256. That keeps the log small and
  free of business data.

The plugin writes through `ekit log append` rather than to the file directly. Hashing, redaction
and rotation then live in one place.

**C. Redaction.** Before writing, values matching the kit's secret patterns (the gitleaks rule set
already shipped for pre-commit) and any argument named like `token`, `secret`, `password` or `key`
become `"***"`. Environment variables are never logged.

### 4.3 Reading it

| Command | Who | Does |
|---|---|---|
| `ekit log tail [-n 50] [--feature F] [--kind K] [--via agent\|person]` | anyone | human-readable recent events |
| `ekit log show <run_id>` | anyone | all events of one run |
| `ekit log why <feature>` | anyone | the timeline for one feature: red attempts and their findings, freezes, glue amendments, blocked records, unfreezes, green attempts. **This is the stall-debugging view.** |
| `ekit log export --since … [--feature F] > bundle.jsonl` | anyone | for attaching to a defect or audit |
| `ekit log verify` | anyone, CI | checks the hash chain, reports the first broken `seq` |
| `ekit log append` | plugin / ekit only | internal |

`ekit doctor` adds a row for the log: present, chain intact, plugin installed. `ekit status` shows
the last event time per feature.

### 4.4 Tamper evidence

Each event's `prev` is the sha256 of the previous line's bytes. The first event of a rotated file
carries the last hash of the file before it. The agent cannot edit `.ekit/*` with its edit tools,
but it could write to the file through the shell. `ekit log verify` detects that. With
`log.commit: true`, CI runs `ekit log verify` as part of `ekit gate green`. That is a new check,
`GREEN-LOG-INTACT`, and it is a warning by default.

## 5. Command and rule changes

- `/speckit.esdlc.red`: run `ekit run typecheck` on the test module before `ekit gate red`, and fix
  type errors first.
- `/speckit.esdlc.implement`: the step-body rule and `ekit blocked` text from §3.5. Remove "never
  touch the test module" in `split` mode, and keep it in `strict` mode.
- `AGENTS.md` block: the same, plus "every action is logged; do not write to `.ekit/`."
- `ekit unfreeze`: in `split` mode it is needed only for `.feature` or contract changes. The
  message says so when a person runs it for a glue-only problem.

## 6. Upgrade from 0.3.0

- `ekit upgrade` vendors kit 0.4.0, installs the plugin, adds `.ekit/logs/` to `.gitignore`, and
  writes `freeze.mode` (`split` for golden, `strict` otherwise).
- Features already frozen keep their 0.3.0 ledger entries, which have no `contract`. For those,
  `GREEN-CONTRACT-INTACT` warns and tells the person to run `ekit freeze --recontract <feature>`.
  That command recomputes the contract from the red-time commit (`git show <git_head>:<file>`), not
  from the working tree.
- Requires `ekit >=0.4.0,<0.5`.

## 7. Measuring it

Add to the runbooks' benchmark arm C (same BRD, same standard-tier model, `split` vs `strict`,
three runs each, arm assigned):

| # | Metric | How |
|---|---|---|
| M17 | Person unfreezes per feature | `cmd.end` events where `cmd` is `unfreeze` |
| M18 | Glue amendments per feature, and the share that passed `GREEN-GLUE-STILL-RED` first time | ledger `glue_amendments`, log |
| M19 | Blocked records per feature, and time to resolve | ledger `blocked` → next red or green |
| M20 | Red attempts rejected by `RED-GLUE-TYPED` / `RED-ROUTE-STUBBED` | log `gate.checks` |
| M21 | Escaped weakening | a reviewer marks a glue diff as weakening that the gates passed (should be 0) |

Decision rule: make `split` the default for generated projects too if M17 falls substantially, M21
stays 0, and M1 (hold-out pass rate) is equal or better.

## 8. Known limits

- `GREEN-GLUE-STILL-RED` runs the feature's acceptance suite a second time on every green with
  changed glue. That costs a few seconds on the golden stack and more on slower stacks.
- `RED-GLUE-TYPED` is only as good as the typing. Untyped helpers or `Any` from a JSON body hide
  errors. The golden step library returns typed values, but generated projects get less from it.
- The OpenCode plugin API (`tool.execute.before` / `after`, and what it exposes about session and
  model) must be **verified against the user's installed OpenCode version** before release. If
  something is missing, the plugin logs what it can. The CLI log (§4.2 A) does not depend on it.
- `via: agent` relies on the plugin setting `EKIT_ACTOR`. Commands a person types in a terminal
  OpenCode does not control are logged as `person`.
- Weakening rules (§3.3) are structural. A step can still be made weaker in ways the AST does not
  show, such as asserting on a different field with the same literal. `GREEN-GLUE-STILL-RED` and
  the committed diff are the backstops.

## 9. Not in 0.4.0

| Item | Why deferred |
|---|---|
| Deterministic glue generation (`ekit red scaffold` from a per-feature step map) | Bigger change. Measure whether split freeze and `RED-GLUE-TYPED` are enough first. |
| Automatic escalation of red to a stronger model after N failed red gates | Needs model routing to read the log. Easy after 0.4.0, since the log provides the count. |
| Waivable red (`red: required \| waived`) | Not needed if split freeze fixes the stalls. Revisit only for non-regulated users. |
| Cucumber-JVM / cucumber-js contract and weakening checks | The AST checks are pytest-bdd only, as with the other `bdd.*` checks. |

## 10. Implementation notes (differences from the draft)

| Area | As built |
|---|---|
| Config | `freeze.mode` and `log.commit` live in `.ekit/project.yaml`. There is no `.ekit/config.yaml`. |
| What `GREEN-GLUE-STILL-RED` replays against | Not red's `git_head`, which is the HEAD **before** red was committed, when the feature's stubs usually did not exist yet. It uses the commit that recorded the red ledger entry (`contract.red_evidence_commit`), falling back to `git_head`. |
| How the replay touches the tree | The current feature package (golden) or source dirs (generated) are copied to `.ekit/replay-backup/<ts>/`. The red-time files are written from `git show`, without touching the git index. The run happens, and the copy is put back in a `finally` block. Uncommitted implementation work survives, unlike `fix-red`, which refuses a dirty tree. If the process is killed mid-run, the copy stays in `.ekit/replay-backup/`. |
| Glue evidence | Diffs are written only when green passes, via `_write_glue_evidence` in `flush_pending_records`, so a failing green leaves no stray evidence files. |
| `GREEN-TESTS-UNCHANGED` in split mode | Still runs, but skips Python glue modules. `.feature` files and non-Python bound files stay byte-compared. |
| Hazards in `GREEN-GLUE-NOT-WEAKENED` | `pytest.skip` / `pytest.xfail` calls; `mark.skip` / `skipif` / `xfail` decorators and `pytestmark`; `assert <truthy constant>`; `assert x == x`; `... or True`; a `try` around an assert with a bare, `Exception`, `BaseException` or `AssertionError` handler; a `return` before the first assert in a `Then` step. Each is counted at red, and green fails if a count goes up. |
| `RED-GLUE-TYPED` | Uses a new profile command, `typecheck_glue` (fastapi: `uv run --locked mypy --follow-imports=silent --show-error-codes --no-error-summary`). It runs on the bound test files only, and reports only logic error codes: `attr-defined`, `name-defined`, `call-arg`, `arg-type`, `return-value`, `union-attr`, `index`, `operator`, `assignment`, `call-overload`, `func-returns-value`, `has-type`. Strict-mode style codes are ignored. Stacks without the command get an info finding. |
| `RED-ROUTE-STUBBED` | Detects 404 from the shared step library's message (`expected <code>, got 404 …`) in the first failed step. A Then that expects 404 is exempt. |
| `ekit blocked` | Writes a `phase: blocked` ledger entry and an `agent.blocked` event. `ekit status` shows `blocked: N open` until a later red or green entry. |
| Action log CLI wrapper | `cmd.start` / `cmd.end` per `ekit` command, except the read-only `ekit log` actions. Gate runs carry check statuses and up to 20 findings. `freeze_feature`, `unfreeze_feature` and `unfreeze_baseline` also write `state.*` events. The `dirty` flag ignores `.ekit/logs/`. |
| OpenCode plugin | Calls `ekit log append --json …` once per tool call (`spawnSync`). That costs one short Python start per agent tool call. It sets `EKIT_ACTOR=agent` for the OpenCode process, so the agent's shell runs of `ekit` are logged with `via: agent`. `outcome` is always `ok`: calls refused by a permission rule are **not** captured, since they may never reach the `tool.execute.*` hooks. |
| Hash chain | Detects edits, deletions and reordering of every line except the last one. Nothing after the final line records its hash. |

### Drafted above but not built in 0.4.0

- `GREEN-LOG-INTACT` (§4.4). `ekit log verify` exists, but it is not wired into a gate. Run it in CI
  yourself if the log is committed.
- `ekit upgrade` does not write `freeze.mode`. The mode is derived instead (`split` when
  `.ekit/golden.lock.yaml` exists), and an explicit value in `.ekit/project.yaml` overrides it.
- `glue_amendments` does not list changed `functions`. The committed diff shows them.
- `tool.call` outcomes `error` / `denied` (see the plugin row above), and the last-event time in
  `ekit status`.
- `ekit unfreeze` does not yet say "glue-only problems don't need this in split mode".
