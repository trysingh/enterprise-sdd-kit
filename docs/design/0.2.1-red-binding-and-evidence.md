# ekit 0.2.1: red binding, committed evidence, landing-zone status

Found on the first real project (an intranet messenger, fastapi-jinja, Windows):

| Gap | What happened | Fix |
|---|---|---|
| Red froze a test that could never pass | A scenario failed at an early step (a stub returned 501), so pytest-bdd never reached `Then "access is forbidden"`, which had no definition. Red recorded a real failure for the wrong reason and froze the test; the gap surfaced only at green. | `bdd.steps_bound` (`RED-STEPS-BOUND`, also `GREEN-STEPS-BOUND` for features recorded red earlier): a static scan that every step of every scenario (Background included, Scenario Outlines expanded per Examples row) has a definition with the right keyword type, visible to the binding module (the module, `conftest.py` files up to the profile root, modules it imports). Patterns: plain string, `parsers.parse` / `cfparse` (converters respected), `parsers.re` (full match), `parsers.string`. A pattern built at runtime cannot be checked: findings for that module become warnings. pytest-bdd only; other runners get an info line. |
| Red evidence not committed | The `.feature` files and the PRD were untracked while implementation went ahead, so the commit the ledger cites did not contain them. | `ledger.red_committed` (`REDREC-COMMITTED` before implementing, `GREEN-RED-COMMITTED` at green): every file fingerprinted at red exists with that content in a commit reachable from HEAD, and the ledger is tracked. Outside a git repository: a warning. |
| Landing zone invisible in `ekit status` | `000-landing-zone` showed as a feature with every column `--`. | A passing `ekit gate baseline` writes `.ekit/ledger/baseline.yaml` (commit, versions, fingerprint of the conformance record, the kit and the active profiles; not rewritten when unchanged). `ekit status` shows *passed / stale / not run* and lists `000-*` smoke scenarios apart from features; `ekit doctor` reports a stale record. With waves, activating a profile makes the record stale until baseline passes again. |
| Two ADRs numbered 0001 | The agent started a new ADR at 0001, so `ADR-0001` in a Waived row was ambiguous. | `adr.unique` in `baseline` and `plan`, naming the next free number. |

Not fixed by the kit (agent output): the PRD slug typo. Command texts now tell the agent to have the user commit
right after red, and to stop at `REDREC-COMMITTED` rather than committing or editing evidence itself.
