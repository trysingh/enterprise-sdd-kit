# ekit 0.2.4: don't record red before the whole gate has passed

Status: implemented in ekit 0.2.4 / kit 0.2.4.

## 1. What this fixes

Using `ekit fix-red` on the same real project that found every gap since 0.2.1 surfaced a bug in
`ekit gate red` itself, not in `fix-red`'s own logic:

1. `fix-red` reverted a feature's production source to its last-red commit and ran `ekit gate
   red`. The scenario failed with an `AttributeError` — broken test glue, not a clean assertion —
   so `RED-CLEAN-FAILURE` correctly rejected the run and the overall gate reported `FAILED`.
2. But a new entry had already landed in `.ekit/ledger/<feature>.yaml`, and the feature had
   already been re-frozen in `opencode.json`. The next `fix-red` run read that entry as "the last
   red," reverted to its `git_head` — and since `git checkout <rev> -- <paths>` never moves
   `HEAD`, that `git_head` was just whatever commit was already checked out (the one *with* the
   implementation). Reverting to it was a no-op: every scenario passed again, immediately, with
   no way forward.

The root cause is in `checks.py`'s `bdd_run` (the `bdd.run` check type, used as `RED-RUN` and
`GREEN-RUN`): it writes its ledger entry and (for red) re-freezes the feature as soon as *its own*
findings are clean — before `RED-CLEAN-FAILURE`, a separate, later check in the same `red` gate,
has had any chance to reject the run. pytest-bdd reports a genuine assertion failure and a step
that errored identically as `"failed"`, so `RED-RUN` sees nothing wrong with either; whether the
run was actually *clean* is exactly what `RED-CLEAN-FAILURE` exists to decide, and by the time it
runs, the record is already written.

This was a latent bug in `ekit gate red` since before `RED-CLEAN-FAILURE` existed (0.2.2) — it
simply had no way to manifest before there was a second check in the same gate that could reject
an otherwise-clean-looking `RED-RUN`. `fix-red` (0.2.3) made it easy to hit in practice, because
retrying the *same* command on the *same* feature is exactly its normal use.

## 2. The fix: queue the write, flush only on a passing gate

- `GateContext` (`checks.py`) gains `pending_records: list[dict]`.
- `bdd_run`, on a clean run with `record: true`, no longer writes the ledger or calls
  `freeze.freeze_feature` itself. It appends the entry's data (`expect`, `want`, `status`,
  `fingerprints`) to `ctx.pending_records` instead.
- `checks.flush_pending_records(ctx, results)` does the actual write (and, for red, the re-freeze),
  appending its notes as info findings onto the originating `bdd.run` `CheckResult` — the same
  place they used to come from, so a verbose report looks identical to before.
- `gates.run_gate` calls `flush_pending_records` right after computing the gate's overall
  `GateResult`, and only `if res.passed` — i.e., only once every check in the gate, including ones
  that run after `bdd.run`, has had its say.

This is a small, general fix at the gate-engine level, not something specific to `fix-red`: any
gate with a `bdd.run` check followed by another check that can reject an otherwise-clean run now
behaves correctly, and any gate without one is unaffected (`ctx.pending_records` stays empty, the
`if res.passed and ctx.pending_records` guard is a no-op).

**Recovery for an already-poisoned ledger** (any project that hit this before upgrading): find the
entry that was recorded moments before a `RED-CLEAN-FAILURE` rejection in the same run — its
`scenarios` map will show `"failed"` for everything, same as a genuine one, but it exists in a
ledger whose gate result for that run was `FAILED` — and remove it from `.ekit/ledger/<feature>.yaml`
by hand. There is no way to tell these apart from the outside after the fact; this is why the fix
is to stop writing them, not to detect and filter them later.

## 3. Also tightened: `fix-red`'s failure message

Separately — and not something this version can fully fix — `fix-red` reverts a feature's *whole*
production source directory (`layout.source`) to its last-red commit, scoped at the directory, not
the file. On a project with more than one feature sharing that directory (this project has three),
that revert can go back further than the fix actually needs: it also undoes whatever shared code
other features added to that same tree since, or an earlier shape this feature's *own* later
implementation work changed — and a test fixed to match the final shape of the code can legitimately
fail with something other than `AssertionError` against an older shape, for reasons that have
nothing to do with whether the test's own glue is right.

`RED-CLEAN-FAILURE` correctly rejects that outcome (it really isn't a clean assertion failure), but
the previous message ("fix the test further and run `ekit fix-red` again") assumed the only
explanation was a bug in the test. `cmd_fix_red`'s message now also names the directory-scope
explanation and points at the narrower manual alternative: revert only the specific file(s) this
feature's own implementation touches, by hand, rather than the whole source tree.

Properly narrowing `fix-red`'s revert scope (e.g. to only the files a feature's own `tasks.md`
names) is deferred — `tasks.md`'s task-to-file mapping isn't structured enough to parse reliably
yet, the same reason 0.2.2 deferred narrowing the source-deny below the whole tree.

## 4. Not in 0.2.4

| Item | Why deferred |
|---|---|
| Scoping `fix-red`'s revert to only the files a feature's implementation touches | Same `tasks.md`-parsing gap 0.2.2 deferred; the improved failure message is the mitigation for now. |
| Detecting a `git_head` that doesn't actually represent a red tree (because a prior `fix-red` recorded it without moving `HEAD`) | No distinguishing information exists after the fact; the fix is to stop writing a bad record in the first place (section 2), not to detect one later. |
